# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Project Does

DebridMovieMapper is a Rust async service that bridges a debrid service — **Real-Debrid or TorBox** — with media servers like Jellyfin and Plex. It fetches torrents from the configured debrid account, identifies them via TMDB metadata, and exposes a WebDAV endpoint serving proxied media files (the actual `.mkv`/`.mp4` bytes are fetched from the provider's CDN on demand). Exactly one provider is active per deployment, selected at startup by which token is set (`RD_API_TOKEN` or `TORBOX_API_KEY`).

Optionally, the library can be **driven by users' Trakt accounts** (SP2): when Trakt sync is configured, each enrolled user's watchlist and in-progress titles auto-acquire content, and a reconciler lifecycle-removes it. A title acquired from a watchlist is removed once it is un-watchlisted and nobody wants it (Trigger B; Trakt drops watched items from the watchlist). A title wanted only as in-progress is removed (Trigger A) only while every in-progress wanter has finished it and it is still wanted: still in `/sync/playback` (a paused re-watch) or, for a show, folded back in by the `REMOVE_FINISHED_SHOWS` finish-cleanup. Trakt drops a finished title from `/sync/playback`, so an in-progress-only movie, or a show with `REMOVE_FINISHED_SHOWS` off, is kept after it is finished. Without Trakt nothing is acquired, but the account mirror, dedup, the best-copy selection repoint and the daily upgrade engine still run over everything already in the account.

**Required environment variables:**
- A debrid provider token — exactly one of:
  - `RD_API_TOKEN` — Real-Debrid API token
  - `TORBOX_API_KEY` — TorBox API token

  Set one or the other, not both. Setting **both** is a startup error; setting **neither** is a startup error.
- `TMDB_API_KEY` — TMDB API key

**Optional:**
- `SCAN_INTERVAL_SECS` (default: 60, minimum: 10) — how often to poll the active debrid provider
- `DB_PATH` (default: `metadata.db`) — path to the redb database file
- `PORT` (default: 8080) — WebDAV server listen port
- `CDN_FIRST_READ_MB` (default: 8, clamped 2–16) — size (MB) of the FIRST read-ahead CDN fetch when a media file is opened. Front-loads the container header + early index so a player's open/ffprobe burst is served from one cold fetch instead of several round-trips (the dominant on-demand-streaming startup cost). Subsequent reads use the normal `BUFFER_SIZE` (2 MB) window. Set `2` to disable the enlargement (= prior behaviour). Wired via `DebridFileSystem::with_first_read_bytes`.
- `RUST_LOG` (default: `info`) — log verbosity via a `tracing-subscriber` `EnvFilter` directive (the `env-filter` feature is enabled). Unset → `info` (unchanged behaviour); a malformed directive falls back to `info` rather than crashing startup. Scope it to this crate to avoid dependency noise, e.g. `RUST_LOG=debridmoviemapper=debug`, or target one module: `RUST_LOG=debridmoviemapper::acquire=debug,info`. Takes effect on (re)start. The acquisition lifecycle is instrumented for `debug`: `acquire` (scrape count, ranked top-3 with cached/resolution/source/seeders, the candidate added, idempotent/lapsed/NoAcceptableRelease outcomes), `observe` (per-tick reason a Pending torrent is still waiting — absent/no-files/selecting/downloading/probe-deferring — plus reaps at `warn` and `Verified` at `info`), `scraper` (candidate counts; never the token-bearing URL), and `tasks` (Trakt wanted-set sizes, reconcile op counts). `dav_fs` playback resolves log at `trace`, since they fire on every file open (e.g. `RUST_LOG=debridmoviemapper::dav_fs=trace`; never the CDN URL).
- `JELLYFIN_URL` — Jellyfin server URL (e.g. `http://jellyfin:8096`)
- `JELLYFIN_API_KEY` — Jellyfin API key
- `JELLYFIN_RCLONE_MOUNT_PATH` — rclone mount path as seen by Jellyfin (e.g. `/media`)

**Optional — Acquisition quality preferences (SP1):** (full descriptions in `README.md`'s env-var table)
- `MAX_RESOLUTION` (default: `1080`) — hard resolution ceiling for acquisition (`720`/`1080`/`2160`, each also accepted with a `p` suffix, or the `2160` synonyms `4k`/`uhd`); candidates above it are excluded.
- `AUDIO_LANGUAGE` (default: `original`) — required audio language: a 2-/3-letter ISO code or `original` (TMDB's original language **plus its listed `spoken_languages`** — any of them is acceptable, for both ranking and the probe; a title with no spoken languages listed behaves exactly as before, original only. An explicit ISO code ignores spoken languages entirely).
- `SUBTITLE_LANGUAGE` (default: unset = `none`) — required subtitle language (ISO code), or `none`/unset to skip the check.
- `PREFER_HEVC` (default: `true`) / `PREFER_HDR` (default: `false`) — scoring preferences for HEVC and HDR/Dolby-Vision encodes.
- `STALL_TIMEOUT_SECS` (default: 1800, minimum: 60) — seconds without download progress before a Pending torrent is re-acquired.
- `MAX_ACQUIRE_ATTEMPTS` (default: 5, minimum: 1) — how many of the top-ranked candidates one acquisition pass tries to add, moving to the next only when the add itself fails. A release later rejected by `observe` (wrong title or audio, corrupt, stalled, dead) is blacklisted and the next-best candidate is tried, so over time every non-blacklisted candidate may be tried.
- `SCRAPER_ADDON_URL` (default: auto-templated from the provider token) — override the Torrentio/Stremio addon base URL.
- `SCRAPER_PROXY_URL` (default: unset) — route ONLY the scraper's traffic through an HTTP(S) proxy (a non-http(s) scheme is a startup error); CDN/TMDB/provider stay direct.
- `SCRAPER_MIN_INTERVAL_MS` (default: 1000, clamped 100–60000) — minimum spacing between scraper requests. Torrentio sends no rate-limit headers and answered 429 once ~80–100 requests arrived within a minute (the hourly episode check scrapes 100–200 episodes back to back), so every scrape is paced through the scraper's own `AdaptiveRateLimiter`; a 429 doubles the interval (honouring `Retry-After`) and is retried, up to 3 requests per scrape, before surfacing as the retriable error. Lower it for a self-hosted addon.

**Optional — Trakt sync (SP2):**
- `TRAKT_CLIENT_ID`, `TRAKT_CLIENT_SECRET` — both required to ENABLE Trakt sync (from a Trakt API app). If either is absent, Trakt sync is disabled and nothing is acquired. The scan loop's account mirror, best-copy selection repoint, same-hash duplicate deletion and dedup (dry-run by default) still run over everything already in the account, and so does the daily upgrade engine (on by default), which adds better cached releases and deletes the copies they replace, user-added torrents included. `UPGRADE_INTERVAL_SECS=0` stops that.
- `TRAKT_SYNC_INTERVAL_SECS` (default: 900, minimum: 60) — Trakt sync + reconcile cadence.
- `TRAKT_EPISODE_CHECK_INTERVAL_SECS` (default: 3600, minimum: 300) — episode-monitor cadence. (Note this exact env var name — it carries the `TRAKT_` prefix for consistency.)
- `TRAKT_CATCHUP_LOOKBACK` (default: unset = all-time) — **catch-up** lookback window. A show you've *watched* (not just watchlisted/in-progress) is auto-acquired to catch up on episodes aired since you last watched it, but only if you last watched it within this window. Accepts `<N>d` / `<N>w` / `<N>mo` (e.g. `90d`, `12w`, `6mo`), a bare number = days, or `0`/unset = all-time (every watched show with unwatched aired episodes qualifies). Anchored on Trakt's per-show `last_watched_at`. A malformed value is treated as all-time (logged at warn), never a startup failure. **Operational cost:** each catch-up candidate costs one Trakt `show_progress` call (plus a TMDB `show_status` call) per sync cycle, so an all-time window over a large watch history issues that many extra requests every `TRAKT_SYNC_INTERVAL_SECS` (the shared rate limiter paces them, so it's absorbed, not an error). Set a bounded lookback (e.g. `90d`/`6mo`) to scope the catch-up set — and the per-cycle API load — to recently-watched shows. **Note:** because it gates the shared per-show `show_progress` check, this window *also* scopes `REMOVE_FINISHED_SHOWS` finish-cleanup — a show last watched outside the window is not a finish-removal candidate (see that option).
- `TRAKT_ENROL_ALLOWED_HOSTS` (default: unset) — extra host names accepted in the `Host` header of the `/trakt` enrolment routes, on top of IP literals, `localhost`/`*.localhost`, single-label names and `.local`/`.lan`/`.internal`/`.home.arpa` names. Any other `Host` gets `421 Misdirected Request` (a DNS-rebinding guard, checked before the CSRF guard, for every method; a request with no `Host` header is allowed). Parsed by `config::parse_allowed_hosts` into `TraktConfig.enrol_allowed_hosts`.

  Accounts are linked via the local-network enrolment page (`/trakt/accounts` on the WebDAV listener), not a static list.

**Optional — Upgrade engine (SP3):**
- `UPGRADE_INTERVAL_SECS` (default: 86400 = daily; `0` disables; minimum 600 when non-zero) — how often to run the quality-upgrade + full-season consolidation pass. On by default; set to `0` to disable entirely.
- `UPGRADE_BUDGET_PER_TICK` (default: unset = no cap, minimum: 1) — cap on the owned titles re-scored per upgrade pass. Unset, every pass visits the whole library: measured on the live library (312 titles), that is ~490 scrapes (~8 min at the 1 s scraper pacing), up to ~2,300 only if every multi-episode pack's sample episode had a better release. The default used to be 20, which put a full rotation at ~16 days, so a copy the pass would replace (e.g. an SD Russian-dub pack serving an English show's episode) waited up to two weeks for its turn. Either way titles needing attention go first (`upgrade::needs_attention`: a `Verified` copy with no recorded quality, an unknown quality — `release::is_unknown_quality` — or `quality.unverified`), each group least-recently-checked first; under a cap they get half of it (rounded down) and the rest goes to the least-recently-checked remaining titles (`upgrade::upgrade_batch`), so attention titles that never find a better copy can't starve the others.
- `UPGRADE_IDLE_SECS` (default: 300, minimum: 30) — seconds without a proxy read before a copy may be swapped, pruned or removed. The upgrade engine checks only the torrents a step changes (`ReadActivity::torrents_idle`): a swap or prune waits while a player has read, within the window, a torrent it deletes or takes an episode away from (`upgrade::copies_serving`: every owned copy of the affected episodes, or of the film, plus what their selection slots point at), and a title with a copy being read is skipped for that pass (cursor unchanged) while the pass moves on to the next title. It used to check the whole library, so on 2026-11-12 Jellyfin probing the file a swap had just added (about 75 s after the swap's notification) stopped the rest of the daily pass. Dedup removals, `execute_remove`, the scan loop's same-hash duplicate deletion and `selection::repoint_to_better_copies` still check the whole library (`all_idle`). **Start-up grace:** read activity is in-memory only, so right after a (re)start there is no read history — for the first `UPGRADE_IDLE_SECS` after the process starts the library counts as **not idle**, so every idle-gated deletion defers instead of firing on the first tick (a redeploy once deleted 81 torrents 34 s after start-up). The upgrade job therefore waits out the grace before its first pass (`scheduler::periodic_after` with `upgrade_first_run_delay`), rather than running a start-up pass that would defer every title and leave the next one a full `UPGRADE_INTERVAL_SECS` away (a service restarted at least daily would otherwise never upgrade).
- `ACQUIRE_DEAD_TIMEOUT_SECS` (default: 600, minimum: 120) — seconds an optimistically-added `Pending` torrent may remain unresolved before `observe` reaps it as dead, blacklists the hash, and re-scrapes.
- `DEDUP_REMOVE_DUPLICATES` (default: unset/`false`) — when `true`/`1`/`yes`/`on`, the duplicate-dedup pass actually **deletes** redundant torrents from the provider. Default is a **dry-run** that only logs the plan (`dedup: …` lines) so it can be reviewed first. Removal is additionally idle-gated (`UPGRADE_IDLE_SECS`, incl. its start-up grace) so it never interrupts an active stream. A copy is only ever removed in favour of copies of the **same or better quality** (quality first — resolution, then source tier, then checked before unchecked, an untagged axis counting as the lowest; see the `tasks.rs` row); pre-existing account-mirror copies get no protection. Only settled (`Verified`) copies take part — a `Pending` acquisition is neither removed nor allowed to displace one.
- `REMOVE_FINISHED_SHOWS` (default: unset/`false`) — when `true`, a fully-watched **Ended** show that isn't watchlisted is auto-removed (Trigger-A finish cleanup), **including shows already in the library**. Default `false` only **logs** the finish-removal candidates (`trakt: <user> — N finished+ended owned show(s) would be removed (preview …)`) without removing — review the preview, then enable. (Mechanism: `sync_trakt` folds the finished+ended owned shows — those Trakt's per-show progress reports caught-up — into the wanted-set only when this is on, so the reconciler's existing Trigger-A removal fires. Trigger A and the acquire-side guard are decided by `user_finished` over the **TMDB** aired set (regular episodes — Specials/season 0 are ignored, see `wanted::SPECIALS_SEASON`) against Trakt's per-episode watched set (read with `extended=progress` — without it every watched set was empty and nothing was ever finish-removed), so removal fires and the acquire path acquires nothing **when TMDB and Trakt agree on the aired episodes**; if TMDB lists an aired episode Trakt's watched set lacks, the show reads as not-fully-watched, is kept, and catch-up acquires that genuinely-unwatched episode — consistent, not a phantom acquire. A watchlisted show is never finish-removed. **Scoped by `TRAKT_CATCHUP_LOOKBACK`:** the finish-cleanup candidate set is built from the same per-show `show_progress` check that the catch-up lookback window bounds, so a bounded lookback *also* scopes finish-cleanup — a fully-watched Ended owned show last watched **outside** the window is neither previewed nor removed. This coupling is deliberate: decoupling it would reintroduce an unbounded per-cycle `show_progress` call for every owned watched show. With the default all-time lookback every finished+ended owned show is considered.)
- `ALLOW_RESOLUTION_DOWNGRADE` (default unset/`false`) — when `true`/`1`/`yes`/`on`, the upgrade engine may perform a **corrective downgrade**: when `MAX_RESOLUTION` is lowered below an owned copy, it replaces that above-ceiling copy with a ceiling-conforming CACHED release and prunes the higher-res copy (idle-gated, and only when such a replacement exists — a sole over-ceiling copy with no conforming cached release is kept). It applies to engine-acquired copies (acquired under a previously-higher ceiling) and pre-existing account-mirror copies alike: a mirrored over-ceiling file has its real resolution recorded (older mirror records stored `quality: None` and are re-derived from their file names — see the account-mirror note), so it is **never treated as unknown-lowest quality** — replacing it is always this gated corrective downgrade. Default is a **dry-run** that only logs the planned downgrades (`upgrade: … would downgrade …`). Pure quality upgrades are unaffected by this flag.

## Architecture

The project is structured as both a binary (`main.rs`) and a library (`mapper.rs` as lib root).

**Background tasks (the scheduler model, SP2):** `main.rs` spawns `scheduler::run`, which spins up cooperating independent jobs over the shared `AppState`. The Trakt/episode/upgrade jobs are each driven by the `scheduler::periodic` primitive (run immediately, then `interval` after each tick completes — a fixed-DELAY cadence — until shutdown; the upgrade job uses `periodic_after`, whose first run waits out the read-activity start-up grace); the scan loop instead runs under `supervise` with its own internal cadence and shutdown-aware awaits:
- **Scan loop** = `run_scan_loop` (every `SCAN_INTERVAL_SECS`, behaviour-preserving): two conceptual sub-steps (NOT separate functions — both inlined in `run_scan_loop`) sharing one `get_torrents` per tick — the *account sync* (poll the active debrid provider → identify torrents via TMDB → `update_vfs` + `record_mirror_owned` + `dedup_owned`) **plus** *acquisition verification* (`engine.observe`). Implemented in `tasks.rs`.
- **Trakt cycle** = `sync_trakt` then `reconcile_wanted` (sequentially, so the reconciler sees the just-synced wanted set), every `TRAKT_SYNC_INTERVAL_SECS`. Spawned **only** when Trakt is configured.
- **Episode monitor** = `monitor_episodes` (every `TRAKT_EPISODE_CHECK_INTERVAL_SECS`). Spawned only when Trakt is configured.
- **Upgrade job** = `run_upgrade_once` (every `UPGRADE_INTERVAL_SECS`, default 86400s/daily, the first pass once the `UPGRADE_IDLE_SECS` start-up grace is over; gated on `UPGRADE_INTERVAL_SECS > 0`): re-scores every owned title (copies of unknown or unchecked quality first; `UPGRADE_BUDGET_PER_TICK` caps it) — including **unknown-quality** copies (no recorded quality, or an untagged resolution/source tier), which rank lowest and are replaced by any known-quality cached within-ceiling release that passes the probe, at or above the copy's resolution when that is tagged (a known resolution stays a floor) — stages meaningfully-better CACHED releases (trying ranked candidates in order until one is usable — in-tick fall-through, like the pack/consolidation paths), and performs a swap of the `selection` (held back while a player reads a copy it changes) + prune of the superseded torrent (for shows: per singleton episode, and per episode served from a within-ceiling multi-episode pack); also consolidates scattered per-episode torrents into full-season cached packs (no quality regression). Disable by setting `UPGRADE_INTERVAL_SECS=0`. Implemented in `upgrade.rs`.

The Trakt cycle + episode monitor are gated on `scheduler::trakt_jobs_enabled` (a Trakt client **and** `config.trakt` both present); otherwise only the scan loop and (unless `UPGRADE_INTERVAL_SECS=0`) the upgrade job run. Nothing is acquired then, but both still act on everything already in the account (mirror, dedup, selection repoint, same-hash duplicate deletion, upgrade swaps and prunes). The local-network Trakt enrolment routes (`/trakt/accounts`) are served on the existing WebDAV listener.

**On-demand (synchronous, during WebDAV file reads):**
- **Repair:** Triggered when a media file is read and `provider.resolve_url` returns `AppError::Unavailable` (RD maps every unrestrict failure except a 401/403 or a 429 to it: a 5xx, a transport failure, a stale-link 4xx such as 404, or a missing link), **or** when the CDN returns a persistent **5xx** on the byte fetch (the file resolved but is broken on the provider, not just a stale URL — after one same-URL retry (no re-resolve) still 5xxs, the byte-fetch path escalates to the same instant repair, once per read, bounded by the repair cooldown). For cached torrents, repair completes inline (~1-2s delay); for non-cached torrents, the file fails and a new torrent is left to download. A persistent 5xx is no longer an endless player retry-storm. A 429 on resolve fails the read without repair. The whole inline repair is bounded to 30 s (`repair::INSTANT_REPAIR_TIMEOUT`): its provider calls use the background retry budgets, so during an outage it could otherwise hold the read for minutes. A timed-out repair returns `RepairFailure::Deferred` and leaves the torrent visible with its attempt budget reset and its cooldown kept.

**Module responsibilities:**

| File | Purpose |
|------|---------|
| `main.rs` | Initializes shared state, spawns the scheduler (`scheduler::run`, which runs the scan loop + the Trakt/episode/upgrade jobs), starts the WebDAV server on port 8080. Connections are bounded by a `MAX_CONNECTIONS` (256) semaphore, and `http1::Builder` sets a `header_read_timeout` (60s) so an idle/dead keep-alive connection can't pin its permit indefinitely (a dead peer would otherwise leak permits until the pool exhausts and the service silently rejects all new connections). The `header_read_timeout` only bounds the HEADER phase, so a peer that dies uncleanly while its connection is **idle** (between range requests, or on a half-open keep-alive slot; no FIN/RST) is reclaimed by **TCP keepalive** (`set_tcp_keepalive`: 60s idle + 3×10s probes ≈ 90s) applied to every accepted socket — otherwise it would pin its permit until the OS retransmission timeout (minutes). (A peer that dies *while* body bytes are being written is reclaimed by the retransmission timer instead — Linux only probes a socket with no unacknowledged data in flight — but the proxy sits idle between its many small range requests, so keepalive covers the dominant case.) Active streams are unaffected (a live peer answers the probes). `--healthcheck` mode issues a real `OPTIONS /` HTTP request (not a bare TCP connect) and requires an HTTP status line within 5s, so a dead or hung accept/handler path reports UNHEALTHY. A saturated connection pool answers 503 and so reads HEALTHY by design (busy, not wedged; a restart would kill every stream); only when the 503-rejecter pool is also exhausted (the connection is dropped) does it read unhealthy. A permanently leaked permit pool is therefore not self-healed by a Docker restart: `header_read_timeout` plus TCP keepalive are what bound permit leaks. It resolves `PORT` via the shared `config::resolve_port` (same logic as the server) so the probe can never target the wrong port. On shutdown the scheduler drain is bounded by an 8s `tokio::time::timeout` so a job parked in a slow provider call / rate-limiter backpressure can't push graceful shutdown past `docker stop`'s ~10s grace into a SIGKILL (scheduler ops are idempotent). |
| `config.rs` | `Config` — all startup env parsing/validation (`from_env`/`from_parts`); shaped for a future DB-override layer. Also parses the optional `TraktConfig` (`Some` only when both `TRAKT_CLIENT_ID` + `TRAKT_CLIENT_SECRET` are present; carries the two Trakt interval knobs plus the optional `catchup_lookback_secs` from `TRAKT_CATCHUP_LOOKBACK` and `enrol_allowed_hosts` from `TRAKT_ENROL_ALLOWED_HOSTS` via `parse_allowed_hosts`). Numeric knobs go through one `parse_num` helper (trim, blank = default, warn + default on a parse error, clamp the whole result) |
| `app_state.rs` | `AppState` — `Clone` bundle of shared handles (provider, tmdb, vfs, store, repair, config, jellyfin, http, scraper, engine, trakt_client, read_activity) carried by the scheduler's jobs |
| `tasks.rs` | `run_scan_loop` — polls the provider, identifies new torrents, updates VFS (+ `engine.observe`), and `record_mirror_owned` (the **account mirror**: every identified present torrent the engine doesn't already track is recorded as an owned record with empty provenance, except a hash the engine has blacklisted for ANY title (hash-wide, `all_blacklisted_hashes`): it is never mirrored, and an existing mirror record with such a hash is reaped (store-only, with its authoritative id + selection slots) until the 30-day blacklist TTL drops the entry — owned + upgradeable, not a protected manual class — so the reconciler sees the user's pre-existing library: no duplicate re-acquire, and a season pack's episodes count as owned). Before that, the mirror pass also **backfills quality** (`backfill_owned_quality`): an owned `Verified` record with `quality: None` (mirrored before quality capture, or recorded `None` for sitting above the ceiling) has its quality re-derived from its torrent's representative file name (axes it leaves untagged filled from the torrent name), atomically and only while still unset (`Store::set_quality_if_unset`) — the upgrade tick runs the same backfill from the persisted identifications. Then `dedup_owned` (the **duplicate cleanup**: `plan_dedup` finds titles covered by more than one present, **settled** (`Verified`) owned hash — a `Pending` acquisition (still downloading, or not yet probed/title-checked) is ignored entirely: never ranked, kept, removed or counted as coverage, so it can't displace a playable copy and is judged once `observe` settles it — and, per title, keeps one + marks the redundant ones for removal — a movie keeps the top-priority hash, a show keeps a greedy episode set-cover so complementary packs are all kept. **Keep-priority = quality first** (`release::quality_rank`: resolution, then source tier, then checked before `unverified` — an untagged axis is 0, so an unknown copy (no recorded quality, or an untagged resolution/source tier) is the lowest at its resolution, while a **known resolution stays a floor**: a 1080p copy with an untagged source outranks a 720p one, and an untagged resolution is the lowest of all) > `quality.score` > currently-served > more episodes > hash; provenance is **not** an axis, so a pre-existing account-mirror copy competes on quality like any engine copy. Dedup never consults `MAX_RESOLUTION` (a copy above it is never ranked down for it), so it never trades resolution down (a corrective downgrade stays the upgrade engine's job under `ALLOW_RESOLUTION_DOWNGRADE`). A show hash is removed only when **every** episode it provides is provided by another kept hash of the **same or better** quality rank (score ignored): the greedy pass runs best-first, and a **second sweep** (lowest-priority first, re-checked against the current kept set so coverage is never lost) reclaims a kept hash that sorted before an equal-quality copy covering it — a better copy is never removed because a worse one covers it (the 2026-11-11 regression). Empty-`provides` hashes are never removed, and a **`Manual`-provenance copy is never placed in the removal set at all** (invariant M-1: manual adds are never auto-removed). Accepted consequence of no mirror protection: when a mirror copy loses to a better engine copy, the title's survival rests on that engine copy, which Trigger A/B may later remove (the lifecycle's own mirror protection — `removal_hashes`/`engine_hashes` — is unchanged). Dry-run by default; `DEDUP_REMOVE_DUPLICATES=true` enables idle-gated deletion + owned-record/selection cleanup). Then `selection::repoint_to_better_copies` (**serve the best copy present**: every existing `selection` slot whose served copy is present, settled and owned is repointed — idle-gated, compare-and-set via `Store::repoint_selection_if` — to another present `Verified` owned copy of the same title that supplies it (lists the episode in `provides` and has an emittable video file with that episode code; a movie: its largest emittable video file) at a STRICTLY higher `quality_rank`, so e.g. a pre-existing or re-added REMUX season no longer hides behind an engine-acquired BluRay pack's slots; no slot is created, nothing is deleted, and equal-rank copies never churn a slot). **Data flow for playback:**
1. Jellyfin/player opens a media file via WebDAV
2. `dav_fs.rs` resolves the file's `FileLocator` to a CDN URL via `provider.resolve_url(&FileLocator)` (cached). Real-Debrid resolves via the locator's restricted `link` (1h cache); TorBox resolves by `(torrent_id, file_id)` via `requestdl` (no per-file link; ~3h cache).
3. `ProxiedMediaFile` fetches bytes from the CDN URL with a 2MB read-ahead buffer (the FIRST fetch per open uses the larger `CDN_FIRST_READ_MB` window) and serves them to the player. A bounded `206` body is read to its natural end so reqwest returns the TCP+TLS connection to the keep-alive pool — the next window reuses it instead of re-handshaking; a Range-ignoring `200` (whole-object) is still read window-bounded then dropped (we can't drain gigabytes).

**Persistence:** Embedded `redb` database (`metadata.db`), created automatically on first run. Some tables can be rebuilt: `matches` (the TMDB identification cache), `blacklist` (TTL'd; losing it only lets rejected releases be tried again), `upgrade_checks` (the upgrade cursor) and `wanted` (rebuilt by the next Trakt sync). The rest are authoritative and exist nowhere else: `owned_hashes` (provenance, `provides`, quality), `authoritative_ids`, `selection` and `trakt_tokens`. Deleting the file loses every Trakt enrolment and the lifecycle provenance: engine copies are re-adopted as empty-provenance mirror records that the Trigger A/B lifecycle won't remove, and managed selections fall back to the VFS default. All `redb` access goes through `store.rs` (the `Store` type); modules never open transactions inline.

## Key Design Decisions

- **Provider abstraction:** All components depend on `Arc<dyn DebridProvider>` (defined in `provider.rs`) rather than a concrete client. `RealDebridClient` and `TorBoxClient` are the two implementations; exactly one provider is active per deployment, chosen at startup by `choose_provider` based on which token (`RD_API_TOKEN` or `TORBOX_API_KEY`) is set.
- **TorBox specifics:** TorBox lists torrents (with files inline) via `mylist`, resolves a file by `(torrent_id, file_id)` via `requestdl` (so `FileLocator.link` is `None`), re-adds by hash via `createtorrent`, deletes via `controltorrent`, and treats `select_files` as a no-op (TorBox auto-selects). A finished download is normalised to `status = "downloaded"` even when its cache has lapsed (TorBox keeps such entries listed as Inactive), so owned-but-uncached films still appear in the library and re-acquire on playback. `mylist?id=` (the single-torrent `get_torrent_info`) can answer a spurious 404 ("No torrents found for this user") for a torrent that exists, so every upgrade staging site looks a freshly-added candidate up through `upgrade::staged_torrent_info`, which retries a 404 after 1, 2, 4 and 8 s (other errors return at once), while `await_downloaded` simply re-polls. TorBox's `progress` (a `0.0–1.0` fraction) is mapped to the canonical `Torrent.progress` as a `0–100` percentage (matching Real-Debrid) so the acquisition engine's stall detector — which resets only on a progress *change* — sees a moving signal for an actively-downloading uncached torrent (without it, `progress` stayed a constant `0.0` and a legitimate download was falsely reaped + blacklisted after `STALL_TIMEOUT_SECS`). The `mylist` response is parsed defensively: per-torrent fields TorBox sends loosely — `size: -1` (metadata not yet resolved) and `files: null` — are tolerated (signed sizes clamped to 0, null fields defaulted) so one malformed entry cannot fail the whole decode and hide the entire library.
- **Provider-neutral file resolution:** The VFS stores a `FileLocator { hash, torrent_id, file_id, file_path, link }` per media file rather than a raw RD link. `resolve_url(&FileLocator) -> Result<String, AppError>` is the single resolution primitive (and `invalidate(&FileLocator)` drops a cached resolution); RD resolves via the locator's restricted `link` (keeping its old unrestrict/cache logic as private inherent methods), while `(torrent_id, file_id)` is used by providers without per-file links (TorBox). `AppError::Unavailable` is the provider-neutral "bytes not currently available → re-acquire/repair" signal — RD maps every unrestrict failure except a 401/403 or a 429 to it (a 5xx, a transport-level failure (timeout/connect, no HTTP status), a stale-link 4xx such as 404, or a missing link), and `dav_fs` drives instant repair off `Unavailable` rather than inspecting an HTTP status.
- **Static linking / scratch Docker image:** The Dockerfile builds with musl targets (`x86_64-unknown-linux-musl`, `aarch64-unknown-linux-musl`) producing a minimal final image on `scratch`. The runtime image's `/etc/ssl/certs/ca-certificates.crt` is unused today (reqwest's `rustls-tls` trusts the compiled-in webpki-roots); it is copied only so a later switch to native roots keeps working on scratch.
- **Adaptive rate limiting:** An `AdaptiveRateLimiter` (token bucket, capacity 1, in `ratelimit.rs`) is shared across a provider's API calls — both `RealDebridClient` and `TorBoxClient` use it. Baseline: Real-Debrid 250 ms (4 req/s; RD documents 250 requests/minute and sends no rate-limit headers, so steady pacing is its only proactive control), TorBox 100 ms (10 req/s). On 429: interval doubles (max 30s under sustained throttling) and `Retry-After` is respected. On success: interval **halves** toward baseline (multiplicative recovery, never below the client's baseline) so a bulk throttle burst doesn't leave later requests crawling at the raised ceiling. **TorBox additionally paces proactively:** `send_data`/`send_ok` read `x-ratelimit-remaining`/`-reset` from every response and call `observe_rate_limit`, holding the next request until the window resets when it is nearly spent — so bulk acquisition stays under TorBox's ~60/window `createtorrent` limit instead of storming into 429s. Real-Debrid sends no rate-limit headers (confirmed live), so it stays on the reactive MIMD path (multiplicative-increase on 429, multiplicative-decrease on success — see `ratelimit.rs`). RD signals throttle as a bare `429` (`error_code 34`, no `Retry-After`); separately, **any 5xx** on `unrestrict/link` (503 is RD's `hoster_unavailable`, `error_code 19`; 500/502/504 are infra errors) is a terminal status (no retry) — this is the synchronous on-read playback path, so it must fail fast rather than run the full ~10-attempt backoff (~3 min) that would surface to the player as a hang. The same path also uses a **small bounded retry budget (3, via `fetch_with_retry_n`)** plus a **10s `connect_timeout`** (separate from the 60s request timeout) so a transport-level hang (timeout/connect) can't stall a WebDAV read for the full ~10×60s window — a dead connect fails over to repair in ~30s instead. Both read-path calls (RD `unrestrict/link`, TorBox `requestdl`) also set a 15 s per-request timeout (`provider::READ_PATH_REQUEST_TIMEOUT`) in place of the clients' 60 s, so an endpoint that accepts the connection and never answers costs 3 × 15 s, not 3 minutes. `resolve_url` maps a 5xx, a transport-level failure (no HTTP status), **and a stale/expired-link 4xx such as 404** (recoverable by a re-add-by-hash) to `AppError::Unavailable` → on-demand repair; a permanent auth 4xx (401/403 bad token) and a 429 that outlasts the 3-attempt read budget stay a hard `Http` error that fails the read without repair (`unrestrict_status_skips_repair`, mirrored by TorBox's `requestdl_status_skips_repair`): a re-add can't fix a bad token, and throttling says nothing about whether the bytes exist, so repairing would re-add (on RD, delete) a healthy torrent inside the throttled window. Note the fast-fail budget bounds the *attempt count and connect phase*, NOT the shared limiter's pre-request wait: since one `AdaptiveRateLimiter` is shared across a provider's calls, under **sustained** throttling a parked `next_allowed` (bounded by `MAX_RETRY_AFTER_SECS` = 300s, and for TorBox by `observe_rate_limit`) can add backpressure latency to an on-read `resolve_url` too. This is deliberate backpressure (a heavily-throttled provider genuinely can't serve the bytes yet) rather than a bug, and is bounded; a dedicated read-path limiter would trade it for a higher 429 rate against the provider.
- **Per-client retry helpers:** `rd_client.rs` has `fetch_with_retry(make_request, terminal_statuses)` (default 10-attempt budget) which delegates to `fetch_with_retry_n(make_request, terminal_statuses, max_attempts)` — callers pass the status codes that should abort without retrying (e.g. 404 for `get_torrent_info`, the full 5xx set — 500/502/503/504 — for `unrestrict_link` so the playback resolve path fails fast to repair). `unrestrict_link` uses `fetch_with_retry_n(.., 3)` (a small budget) so a transport-level hang can't stall a WebDAV read for the full ~10×60s window. `torbox_client.rs` has `send_data`/`send_ok`, which rate-limit, retry on 429/transient errors, and unwrap TorBox's `{success, detail, data}` envelope.
- **Identification scoring:** `identification.rs` cleans filenames extensively before TMDB lookup. Shows vs. movies are detected by file structure (presence of multiple video files with episode patterns). A TMDB search returns a `SearchOutcome` that distinguishes a genuine empty result (a real "no such title") from a **failed** request (`Unavailable` — a transport error / sustained 5xx). During a TMDB outage `identify_name` short-circuits its multi-stage fallback ladder (CamelCase split / prefix strip / after-dash / no-year retry) on the first `Unavailable` rather than re-issuing a full ~2.5-min retry cycle per stage (which would burn ~10 min of doomed retries on one unidentifiable torrent); a genuine empty result still drives the whole ladder. `identify_name` returns `Identification::{Identified, NoMatch, Unavailable}`. `Unavailable` means nothing matched and a TMDB search failed (an outage past the client's retry budget, or a 4xx such as a rejected API key), so it is no verdict on the name. `identify_torrent` skips the torrent-name retry once TMDB is unreachable; `identify_torrent_checked` reports `provisional: true` for such a fallback (`external_id: None`), and a caller should not persist it as the torrent's identification. A torrent left unidentified because a TMDB search FAILED (`tmdb_client::track_search_failures`) is not cached: the scan loop shows it under its fallback title and identifies it again after 15 minutes (`TMDB_RETRY_AFTER`); a genuine no-match is cached as before.
- **Synchronous instant repair (provider-neutral):** When a media file is read, `dav_fs.rs` resolves the locator via `provider.resolve_url` (cached, so free when healthy). On `AppError::Unavailable`, it calls `repair_manager.try_instant_repair(&FileLocator) -> Result<FileLocator, _>` synchronously — re-adds the torrent by hash, selects the same files, and checks if the replacement is already cached. Success is decided by the new torrent reaching `status == "downloaded"` **plus** a `file_path` match for the same file (there is no `InstantRepairResult` type, and no RD-specific link-count check — path matching is inherently safe, and the replacement file is located by matching `file_path` rather than the old positional index into RD's `links` array). On success it returns a fresh `FileLocator` for that file — pairing the per-file restricted `link` by position among selected files for RD, or leaving `link: None` for providers that resolve by `(torrent_id, file_id)` (TorBox). `dav_fs` installs the returned locator (invalidating the old resolution) and re-resolves inline, so playback continues after a brief delay. The repair is bounded to 30 s (`INSTANT_REPAIR_TIMEOUT`); on timeout the torrent stays `Healthy`/visible with its attempt budget reset, and an RD new-id torrent the timeout leaves behind is collapsed by the scan loop's same-hash duplicate deletion. If **not** cached on a genuinely-new id (RD), the file fails, the new torrent is left to download, the old torrent is marked Broken, and the replacement is recorded (scan loop picks it up). **Same-id re-add (TorBox):** TorBox's `createtorrent` recovers the existing torrent by infohash, so a repaired-in-place torrent keeps its **same** id (`new == old`); the repair therefore never deletes it (deleting would destroy the very torrent it repaired — and for mirror/manual content that would be permanent loss), records no replacement, and passes `protect_id` to `reacquire::materialise` so a transient post-add failure can't delete the real torrent either. **Visible on no-replacement failures:** a repair that produces no usable replacement (a transient re-add/info error, or a same-id torrent that's merely re-downloading) leaves the torrent **`Healthy`/visible**, NOT `Broken` — because `read_bytes` short-circuits on `should_hide_torrent` *before* any I/O, a hidden torrent can never re-trigger repair, so marking it Broken with no replacement would trap it until restart. `Broken` is set ONLY where a replacement IS recorded (the not-cached new-id path). **Cooldown + attempt cap survive re-adds:** the repaired torrent's health carries the old entry's `repair_attempts` plus a fresh cooldown trigger to the new id (RD mints a new id each repair), so the 30s cooldown + max-3-attempt cap hold *across* re-adds — bounding a still-broken-on-CDN cached file to ≤3 re-adds rather than a per-read storm. A confirmed good byte read (`note_read_success`, called once per opened file) **resets** the budget, so the cap counts only *consecutive* failed repairs (a storm), not unrelated incidents over the deployment's lifetime (which would otherwise accumulate to a permanent `Failed`).
- **Repair hides broken torrents (provider-dependent):** On the not-cached repair path with a genuinely-NEW id (Real-Debrid), the old torrent is marked Broken and hidden from WebDAV until the scan loop picks up the recorded replacement. On a SAME-id re-add (TorBox's `createtorrent` recovers the existing torrent by infohash), and on any repair failure that records NO replacement, the torrent is instead kept `Healthy`/visible — because a `Broken`/hidden torrent can never re-trigger repair (reads short-circuit on `should_hide_torrent`), so hiding it with no replacement would trap it until restart (see the instant-repair design decision below).
- **SP1 Acquisition Engine (historical — superseded by the SP3 optimistic-add model below; `acquire` no longer materialises/validates/probes synchronously, it adds the best candidate and defers the verdict to `observe`):** When a title is requested (by the SP2 Trakt reconciler — `reconcile_wanted`/`monitor_episodes` — which replaced the temporary `--acquire` CLI), the engine originally ran: (1) **Scrape** — `TorrentioScraper` calls a Stremio-compatible addon (default: Torrentio, URL auto-templated from `<provider>=<token>`; override with `SCRAPER_ADDON_URL`). (2) **Score/rank** — `release::parse` extracts resolution, codec, HDR, size, seeders, cached flag, and source tier; `release::rank` hard-filters the resolution ceiling (`MAX_RESOLUTION`), cam/telesync/screener sources, **and uncached zero-seeder (undownloadable) releases** (so the engine never burns acquire attempts on dead torrents or leaves "checking" magnets behind), then sorts by a weighted score: cached availability dominates, then **resolution within the `MAX_RESOLUTION` ceiling** (a user who raises the ceiling to 2160p wants 4K, so resolution outweighs source tier), then source tier [REMUX>BluRay>WEB>HDTV], then progressively smaller **additive** bonuses — HEVC (+5k), HDR (+3k), verifiable container (+2k), bitrate (up to +3k), seeders (up to +2k) — which **combine into the weighted sum rather than forming a strict tie-break chain** (e.g. the HEVC bonus can outweigh a one-step source-tier difference, and bitrate can outweigh the container bonus), with a configured-`AUDIO_LANGUAGE` mismatch applied as a large penalty; see `release::score` for exact magnitudes. (The default `AUDIO_LANGUAGE=original` is resolved per-title via `QualityPrefs::with_resolved_audio(original_language, spoken_languages)` **before** ranking — to `Lang(x)` when the title's TMDB original ∪ spoken languages (`config::original_audio_languages`: de-duplicated, original first) is one language, `AudioReq::AnyOf(..)` when several (never produced by parsing the env var), unchanged `Original` when none is known — exactly how `probe::verify` resolves `Original` — so a wrong-language release is down-ranked up front rather than ranking #1, getting optimistically added, and only then being rejected at probe time; a release in a spoken language (e.g. a `fi`-original film whose dialogue is mostly English) is not penalised. Accepted trade-off: a dub in a secondary spoken language is accepted too.) (3) **Materialise** — re-adds the torrent by hash, waits for the file list, and selects the target file; **a movie request whose materialised torrent has more than one feature-sized video is rejected as a multi-movie pack** (providers like TorBox auto-select all files). (Post-SP3 only `repair.rs` calls `reacquire::materialise`; `acquire`/`observe` add optimistically.) A candidate whose materialise *fails* (provider "already queued", or an add whose file list never resolves) has any leaked torrent for its hash deleted before the next candidate is tried, so a rejected/failed candidate never lingers as a dead "checking" torrent. (4) **STRICT title validation** — `TmdbTitleValidator` runs `identify_name` on the selected file's name and verifies the result resolves to the requested TMDB id; mismatches are blacklisted and the next candidate is tried. (5) **File-probe** — `HttpProber` fetches the first 4 MB of the CDN URL and uses the hand-rolled `probe::probe_tracks` (MKV/MP4) to extract audio/subtitle language codes; corrupt probes are blacklisted, wrong-language probes are blacklisted, unknown formats are accepted. (6) **Outcome** — `Acquired` (cached + verified), `Pending` (downloading or probe deferred), `NoAcceptableRelease`, or `TemporarilyUnavailable`. `observe` monitors Pending torrents each scan tick: stall detection (no progress for `STALL_TIMEOUT_SECS`), deferred probe retry (up to `MAX_VERIFY_ATTEMPTS`), and fail-and-reacquire. The `authoritative_ids` table overrides filename identification for engine-owned torrents; the `blacklist` table prevents re-adding rejected hashes.
- **Trakt-driven desired state (SP2):** A persisted `wanted` set (per user, per **(media_type, tmdb_id)** — so a movie and a show that share a numeric TMDB id are tracked independently; which sources want it — watchlist / in-progress — plus watched-state and, for shows, TMDB status, **and the IMDB id Trakt supplied**) is materialised from each enrolled user's Trakt account by `sync_trakt`, from reads that follow **every page** (Trakt paginates the watchlist + watched endpoints by default since 2026; a failed page fails the read — see the `trakt_client.rs` row) with watched shows requested as `extended=progress` (the only form that still carries per-episode watched state). **Catch-up source:** a show you've *watched* (from `/sync/watched/shows`) is also folded into the wanted-set as an in-progress source — so episodes that aired since you last watched are auto-acquired — gated by `TRAKT_CATCHUP_LOOKBACK` (last-watched within the window; default all-time) and skipped when the show is already watchlisted (the watchlist already wants its whole run). The catch-up membership is **precisely gated on Trakt per-show progress** (`GET /shows/{trakt_id}/progress/watched`): a within-lookback watched show is folded in **only if Trakt reports it has ≥1 unwatched aired episode** (`next_episode` non-null = behind), so fully-caught-up shows don't bloat the wanted-set or drive a fruitless reconcile each cycle. The progress check runs in `sync_trakt_user` (one call per catch-up candidate; on a missing Trakt id / progress error it conservatively includes the show — degrades to lookback-only rather than dropping a possibly-behind title) and is passed to the PURE `build_wanted` as the fold set. **Finish-cleanup fold:** a caught-up (not-behind) watched show that is **owned AND `Ended`** is a finish-removal candidate; `sync_trakt_user` LOGS these every sync (a preview) and — **only when `REMOVE_FINISHED_SHOWS` is set** — also folds them into the wanted-set so the reconciler's Trigger-A finish removal fires (removal + zero acquisition hold **when TMDB and Trakt agree on the aired set**; on a TMDB/Trakt aired-set disagreement the TMDB-authoritative reconcile keeps the show and catch-up acquires the genuinely-unwatched-per-TMDB episode instead — consistent, not a phantom acquire). When the flag is off they're preview-only and never folded, so nothing is removed. `finished_ended_candidates`/`shows_to_fold` are the pure helpers. A catch-up show acquires only the **unwatched** aired episodes (you want what you haven't seen); a **watchlisted** show acquires **every** aired episode (the whole run, even already-watched, for a re-watch); and `reconcile_title`'s Show branch won't acquire a show all watchers have *finished* (symmetry with Trigger A — a watchlisted show is never "finished", so it still acquires). **IMDB resolution prefers Trakt's id** (`WantedRecord.imdb_id`, carried through to the `Acquire` op) over re-deriving it from TMDB's `external_ids`, because TMDB's mapping is incomplete for some titles (e.g. a TVDB-only show) — `build_acquire_request` falls back to TMDB only when Trakt gave none, and returns `Ok(None)` (skip quietly, logged at debug — Torrentio is IMDB-keyed so it can't be scraped) when no IMDB id exists anywhere, rather than WARN-ing every reconcile tick. A PURE reconcile-core (`wanted.rs`) diffs wanted-vs-owned-and-available and emits acquire/remove `Action`s, executed by `reconcile_wanted` (movies incl. their Trigger-A/B removal + show Trigger-B removal) and `monitor_episodes` (show episode acquisition + Trigger-A finish removal, via TMDB air dates). There is **one shared household library**: acquisition is the union across users; removal is per-user-aware.
- **Removal lifecycle:** The Trakt lifecycle (Trigger A/B) removes only engine-acquired hashes (`removal_hashes` → `OwnedGroup.engine_hashes`), except a show finish-removed under `REMOVE_FINISHED_SHOWS`. Account-mirror copies (torrents the user added; empty provenance) are otherwise kept by the lifecycle, but can still be removed by dedup, by the upgrade prune when a better copy supersedes them, and by `REMOVE_FINISHED_SHOWS` finish-cleanup. `Manual` provenance exists only on legacy records from the removed `--acquire` CLI; it is never auto-removed (M-1, `Provenance::has_manual_entry`). **Trigger A (finished):** every user who **in-progresses** the title has finished it (movie watched; show = 100% of *aired* episodes watched AND its TMDB status is `Ended` (ended or cancelled — `ShowStatus::Ended`; a returning/in-production/planned show never qualifies even if fully watched)). Trigger A needs a current wanter, and Trakt drops a finished title from `/sync/playback`, so in practice it fires only for a title still in `/sync/playback` while already watched (a paused re-watch) or for a show folded back in by `REMOVE_FINISHED_SHOWS`; an in-progress-only movie whose wanted row is gone is kept (pinned by `wanted::tests::finished_in_progress_movie_no_longer_wanted_is_kept`). **A watchlisted title is NEVER finished-removed** — the watchlist is an explicit "keep this available" signal (re-watchlisting something you've watched means you want to re-watch it), so it stays acquired regardless of watched state and `trigger_a_finished` short-circuits to `false` while any user watchlists it. Without that guard a watched+watchlisted title oscillated acquire↔remove every reconcile tick (the acquire path ignores watched), flapping the library. **Trigger B (abandoned):** a watchlist-provenance user un-watchlisted it AND no user currently wants it (via either source) — this is the sole removal path for a watchlisted title. Otherwise the title is kept. Provenance is **sticky** — recorded at acquire time (one entry per wanting user+source) and preserved across re-acquire, including any `Manual` entry. Both removal triggers are executed through the **idle-gated** `execute_remove` (`UPGRADE_IDLE_SECS`), so a removal never tears content out from under an active stream (a non-idle library defers the removal to a later tick, leaving the owned record intact for retry).
- **Availability re-acquire:** A wanted title that is owned but no longer present in the provider listing is treated as lapsed (cache expired / lost) and proactively re-acquired. For shows this is per episode: an episode counts as covered only while a record that supplies it is present or still `Pending`, so an episode whose only copy left the account is re-acquired even while the rest of the show is present (`plan_episode_actions`).
- **Account mirror = owned (no protected "manual" class):** The scan loop's `record_mirror_owned` records every identified, present provider torrent the engine doesn't already track (except a hash the engine has blacklisted for ANY title, hash-wide via `all_blacklisted_hashes`, which is never mirrored; an existing mirror record with such a hash is reaped, store-only, with its authoritative id + selection slots, until the 30-day blacklist TTL drops the entry) as a **`Verified` owned record with EMPTY provenance** (a show's `provides` = the SE-parsed set of its selected video files; a movie's is empty; `quality` is **derived from the representative/largest video file**, with any axis its name leaves untagged filled from the torrent name (`mirror_quality` → `QualitySummary::of_owned`) — `cached: true` since it is present — so the record is comparable on the dedup/upgrade/consolidation paths: an axis neither name tags is recorded as 0 (**unknown — the lowest quality** at its resolution, so a known cached release at or above that resolution that passes the probe may replace it), a file **above the resolution ceiling keeps its real resolution** (never unknown-lowest; replacing it is a gated corrective downgrade), and it is `None` only when there is no video file (a lapsed TorBox entry lists none; it stays unknown-lowest, so a playable copy is never removed in its favour). Older mirror records stored `None` for all of those cases; `backfill_owned_quality` re-derives their quality from their file names (scan loop + upgrade tick; only a still-`None` record is written). A recorded quality is flagged `unverified` iff the representative file isn't `.mkv`/`.mp4` (a mirrored MKV/MP4 was never probed either but is assumed fine — flagging it would churn the whole library) — set when the mirror record (or a backfilled quality) is created, so it covers mirror copies recorded from schema v8 on; a pre-existing mirror copy that already had a quality is **not** flagged retroactively (it has no `selection` entry for the v8 migration to find, and `record_mirror_owned` only fills a missing quality, never rewrites one); `imdb_id` resolved from TMDB `external_ids`, cached per-title, best-effort; an id lost to a transient failure is filled by the daily `backfill_missing_imdb_ids`). This makes the reconciler/episode-monitor aware of the user's **pre-existing library**, so a watchlisted/in-progress title that is already present is **not re-acquired as a duplicate**, and a pre-existing season pack reports its episodes as owned (no per-episode `monitor_episodes` churn). Empty provenance means the record is owned **exactly like an engine-acquired title** — eligible for the daily quality-upgrade / consolidation path (deliberately NOT a `Manual` protected class, so manually-added content follows the same upgrade path) — while still being **kept** under the normal lifecycle: with no Trakt wanter and no watchlist provenance, neither removal trigger (`trigger_a_finished`/`trigger_b_abandoned`) fires for a mirror-only group, and Trigger **B** (abandoned watchlist) never deletes a mirror hash even when it shares a `tmdb_id` with watchlist-acquired episodes (removal is scoped to the group's engine-acquired hashes — `OwnedGroup.engine_hashes` — via `removal_hashes`). It is idempotent and non-destructive — an engine-owned or already-mirrored hash is never clobbered. `observe`'s dead-torrent re-acquire skips only records with **no IMDB id** (can't re-scrape → leave for on-read repair), not by provenance. **A mirror hash (empty provenance) is protected from the general Trakt removal lifecycle**, even when a Trakt user *wants* the title (it shares the `tmdb_id`): a genuine in-progress re-watch (the title is in `/sync/playback` AND already watched) must never delete content the engine didn't acquire. `removal_hashes` enforces this — for a `Finished` (Trigger A) removal it returns only the group's **engine-acquired** hashes (`OwnedGroup.engine_hashes`) EXCEPT in the one opt-in case: a **show** with `REMOVE_FINISHED_SHOWS=true`, where the finish-cleanup *folds* fully-watched ended owned shows into the wanted-set specifically to reclaim the full set (incl. pre-existing library copies). Trigger **B** (abandoned watchlist) also returns only engine hashes. So a mirror torrent is removed only by (a) the explicit duplicate-dedup pass (where it gets **no** protection — it competes on quality like any engine copy) or the upgrade engine superseding it with a better release, (b) `REMOVE_FINISHED_SHOWS=true` show finish-cleanup, or (c) when it is *also* engine-acquired (mixed group) and that engine hash is reclaimed. A pure-mirror **movie** is never finish-removed (movies are never folded). `reconcile_title`'s symmetric acquire-side guard (both the Movie and Show branches short-circuit on `trigger_a_finished`, except for manual content) means an engine-reclaimed title is **not** re-acquired the next tick — no acquire↔remove flip-flop; to keep a watched title available, watchlist it.
- **Multi-user enrolment:** Accounts are linked via device-flow OAuth on the local-network enrolment page (`/trakt/accounts`, served on the WebDAV listener — no auth, trusted-LAN model; the routes answer only for local-network `Host` names, plus `TRAKT_ENROL_ALLOWED_HOSTS`, and reject cross-origin POSTs). Tokens are refreshed once they expire within `REFRESH_BUFFER_SECS` (1 h): Trakt access tokens last 24 h, and a longer buffer would refresh, and rotate the single-use refresh token, on every sync. Tokens are keyed by Trakt **slug**. A token-refresh or read failure — including a failure of **any page** of a paginated read, or a list that changed mid-read — marks the account `needs_reenrolment` (surfaced on the page; cleared by the next successful sync) and leaves its prior `wanted` set intact — the reconciler never acts on a failed or truncated fetch.
- **`--acquire` CLI removed:** The temporary SP1 verification CLI was deleted in SP2; Trakt sync + the reconciler are the acquisition triggers now. A `scheduler.rs` source-guard test (`acquire_cli_is_removed`) fails if the flag is reintroduced into `main.rs`.
- **Database is self-healing (but only for genuine corruption):** `Store::open` stamps a schema version and runs forward migrations. A genuinely corrupt / damaged `metadata.db` (a bad-header `Io(InvalidData)`, a truncated file, redb's `Corrupted`/`RepairAborted`) is **moved aside** to `<db_path>.corrupt` (or `<db_path>.corrupt.<n>` when that name already exists, so an earlier backup is never clobbered) and recreated rather than crashing the service. The old file is kept as `<db_path>.corrupt`, but the recreated DB starts without the Trakt enrolments, provenance, selections and blacklist (only the `matches` cache regenerates), so this is not lossless. A truncated file whose intact header records a longer layout makes redb panic inside `Database::create`; `try_open` catches the panic and treats it as corruption. authoritative tables added in later phases are migrated, never silently dropped (e.g. v7→v8 rewrites owned records in place to flag `quality.unverified` on those a `selection` entry serves from a non-MKV/MP4 file — engine-acquired copies; pre-existing account-mirror copies have no selection entry and are not flagged retroactively). A **transient/incompatible** open failure — another instance holding the lock (`DatabaseAlreadyOpen`), a permission/disk I/O error, an intact database in an older `redb` on-disk format (`UpgradeRequired`, e.g. after a `redb` dependency bump), an intact database in a NEWER `redb` on-disk format (redb reports it as `Corrupted("Expected file format version <= N, found M")`, which `db_open_failure` classifies as transient), **or a schema written by a NEWER build of this app** (our stored schema version is ahead of the binary, e.g. after a rollback) — is classified separately (`db_open_failure` / the `try_open` version check) and **fails startup** instead of discarding a possibly-intact database (its authoritative `owned`/`wanted`/`trakt_tokens`/`selection` tables are not regenerable, so the operator rolls the binary forward / backs up / migrates rather than losing them). The newer-schema case is treated like `UpgradeRequired` — intact-but-unusable, never moved aside — matching `from_database`, which also refuses a newer-than-supported schema.
- **SP3 — Optimistic-add + asynchronous reconcile (always-on robustness + daily quality):** `acquire` now **adds the best candidate optimistically** and records it `Pending` — no synchronous 15s poll, pack-guard, title-validation, or probe. `observe` (every scan tick, no scraping) is the resolver: once files appear, the deferred gates run; on pass it marks `Verified`, records `provides` (which `(season, episode)` pairs the hash supplies) and a `quality` summary, and writes `selection` entries; on fail it blacklists the hash and re-scrapes for the next-best candidate. Genuinely-dead torrents (provider error status, or no resolution after `ACQUIRE_DEAD_TIMEOUT_SECS`) are reaped and re-scraped. **Selection inversion:** "which release represents this title/episode" is a persisted `selection` table (slot → `{hash, file_path}`) that `vfs::build` consults on every scan; a slot with no managed selection keeps the pre-SP3 behaviour (a movie's largest streamable torrent; every distinct file name of an unmanaged show episode). **`provides` kills season-pack churn:** the union of `provides` across a show's owned hashes is the owned-episode set — a season pack reports all its episodes as owned so `monitor_episodes` never re-acquires them. **Daily upgrade engine** (`upgrade.rs`, on by default, disable with `UPGRADE_INTERVAL_SECS=0`): re-scores every owned title each pass (copies of unknown or unchecked quality first; `UPGRADE_BUDGET_PER_TICK` caps it) and stages a meaningfully-better CACHED release (`is_target_improvement`: uncached→cached, or a strict `score` gain on a category jump — a higher resolution, or a higher source tier at the same resolution: never trading resolution for tier, nor tier for a bonus — that still holds with the candidate scored under the title's resolved audio as acquisition ranks it, so a wrong-language-tagged release acquisition would rank below the owned copy is never adopted — or, for an owned copy flagged `unverified` (its tracks couldn't be checked), any equal-or-better cached release at the same-or-higher resolution — or, for an owned copy of **unknown quality** (none recorded, or an untagged resolution/source tier: the lowest quality), any known-quality cached within-ceiling release at or above its tagged resolution; an unknown candidate never improves anything cached, and an over-ceiling copy is never unknown); staging adopts only a probe `Pass`, so an upgrade never swaps a checked copy for an unchecked one; idle-gated swap (`UPGRADE_IDLE_SECS`) + prune of the superseded torrent ensure an active stream is never interrupted. **Shows now get the same quality-upgrade treatment as movies, at per-episode granularity:** every owned singleton episode is independently re-scored and swapped, run BEFORE that season's pack/consolidation handling so a freshly-upgraded episode can still be folded into a pack later the same tick. **Episodes served from a within-ceiling multi-episode pack** are then re-scored against the pack's quality and moved to a better cached true singleton at the same-or-better source tier and resolution (consolidation's no-regression test; since no upgrade lowers a single's tier at the same resolution, consolidation never folds the split pack back — bar one re-fold of an unverified pack split into equal-quality singles) the same way; the pack is pruned only once it serves no slot and every episode it provides is held by another `Verified` owned record that is still present on the provider (otherwise kept), with a sample-first bound (an unimprovable first served episode skips the rest of that pack this visit). **Corrective downgrade (opt-in):** when `MAX_RESOLUTION` is lowered below an already-owned copy's resolution, `effective_score` penalises that copy so a within-ceiling CACHED candidate now reads as an improvement (`Improvement::Downgrade`); this only executes swap+prune when `ALLOW_RESOLUTION_DOWNGRADE=true`, applies to both a movie/episode singleton AND an over-ceiling season pack (`correct_over_ceiling_packs`, same same-episode-coverage + idle-gated-swap discipline as consolidation), and is a no-op — logged as a preview (`upgrade: … would downgrade …`) — when unset (the default) or when no conforming cached replacement exists (a sole over-ceiling copy is kept, never deleted with nothing to replace it). **Full-season consolidation (unchanged, layered after the per-episode passes):** the same engine finds a CACHED full-season pack covering all aired episodes at same-or-better quality and consolidates scattered per-episode torrents into it, idle-gated; consolidation itself never regresses quality and is not part of the downgrade path.

## Development Process

- **Test-Driven Development (TDD) is required.** When implementing new features or fixing bugs:
  1. Write a failing test first that captures the expected behavior.
  2. Write the minimum code to make the test pass.
  3. Refactor while keeping tests green.
  4. Run `cargo test` after every change to confirm nothing is broken.
- **Before every commit, run the lint gate (this is CI's `lint` job — fmt + clippy):**
  ```bash
  cargo fmt --check && cargo clippy --all-targets --locked -- -D warnings
  ```
  CI runs these on the latest stable Rust (`dtolnay/rust-toolchain@stable`), and each new stable
  can add clippy lints — so keep your local toolchain current (`rustup update stable`), otherwise
  lint can pass locally yet fail in CI on a lint your older clippy doesn't have. Cargo.toml's `rust-version` (1.96) matches the Dockerfile builder (`rust:1.96-slim`), so clippy's `incompatible_msrv` lint fails the lint job on a std API newer than the image's compiler. Bump the two together. If
  `cargo fmt --check` fails, run `cargo fmt` to fix; do not hand-format around it.
- **Before every commit, run all unit and integration tests:**
  ```bash
  cargo test --locked \
    && INTEGRATION_TEST_LIMIT=10 cargo test --test integration_test -- --ignored \
    && cargo test --test repair_integration_test -- --ignored \
    && cargo test --test lifecycle_test -- --ignored \
    && cargo test --test probe_integration_test -- --ignored
  ```
  Integration test binaries must run sequentially (not `-- --ignored` on all at once) because they share the live provider accounts and their rate limits, and the ignored set also holds the interactive Trakt test and full-library scans. The live provider tests skip a provider whose token is unset or blank, so configure only the providers you hold a live account for and blank a lapsed token: while Real-Debrid premium is lapsed, run the gate with `RD_API_TOKEN=` exported (a blank exported value beats `.env`, since dotenvy doesn't override). The Real-Debrid-only binaries (`integration_test`, `repair_integration_test`) then skip every test; a set token the provider rejects still fails. Do not commit if any test fails. (CI and the Docker build run with `--locked` — if you bump `Cargo.toml`, run `cargo test --locked` / `cargo build --locked` locally too so a stale `Cargo.lock` is caught before CI rather than silently updated.)
  - `lifecycle_test` is the cross-provider add→appears→delete→disappears check, plus a `lifecycle_acquire_sintel_by_imdb` test that exercises the SP1 `AcquisitionEngine` end-to-end against the live provider. It runs against **both** Real-Debrid and TorBox, **modifying the live account** (adds and deletes a Creative-Commons *Sintel* torrent, cleaning up after itself). Each provider's sub-test **skips** if its token (`RD_API_TOKEN` / `TORBOX_API_KEY`) is unset or blank, so it is safe to run with only one provider configured. The binary's tests hold a shared mutex (`LIVE_ACCOUNT`), so the default parallel harness never has two of them adding and deleting Sintel in one account, and they clean up through `common::with_cleanup`, which also runs when an assertion fails. `lifecycle_acquire_sintel_by_imdb` builds its VFS from the acquired torrent alone and asserts that torrent is under `Movies/`; with a provider token set, a missing `TMDB_API_KEY` or a TMDB failure fails it. (A production deployment sharing the TorBox account can still race the test with its own dedup of the briefly-present Sintel copies; a failure at "should appear in get_torrents()" is usually that, so rerun once.)
  - `repair_integration_test` (Real-Debrid only) also **modifies the live account**: `test_instant_repair_of_sintel` adds the Creative-Commons *Sintel* torrent, marks it broken, instant-repairs it (on Real-Debrid the repair re-adds the hash under a new id and deletes the original) and deletes every Sintel copy afterwards, also when it fails. It never repairs one of the account's own torrents. `test_broken_torrents_hidden_from_webdav` only reads the account.
  - `integration_test` (Real-Debrid only) only reads the account; it caches identifications through `Store` at `$CARGO_TARGET_TMPDIR/integration_test_cache.redb`, never in the service's `metadata.db`.
  - `probe_integration_test` probes a cached *Sintel* file through BOTH providers' CDNs and asserts the probe reaches a verdict without deferring, guarding the 206/200 range-response handling. It runs RD + TorBox, each skips if its token is unset or blank, and it cleans up after itself.
- **Integration tests must be updated for new functionality.** When adding or changing features, update the integration tests to cover the new behavior. Integration tests are the final gate before committing.

- **Interactive Trakt live integration test** (`tests/trakt_integration_test.rs`): validates every Trakt parser and `sync_trakt` end-to-end against a real account without requiring a pre-existing token. Run with `cargo test --test trakt_integration_test -- --ignored --nocapture`; the test prints a URL + code, waits until you open it and approve on trakt.tv/activate, then exercises all reads, asserts that watched shows carry their per-episode watched data (the `extended=progress` regression guard) and that the `wanted` set is populated. Requires `TRAKT_CLIENT_ID`, `TRAKT_CLIENT_SECRET`, and `TMDB_API_KEY`; skips cleanly if any is unset.
