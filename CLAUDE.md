# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Project Does

DebridMovieMapper is a Rust async service that bridges a debrid service — **Real-Debrid or TorBox** — with media servers like Jellyfin and Plex. It fetches torrents from the configured debrid account, identifies them via TMDB metadata, and exposes a WebDAV endpoint serving proxied media files (the actual `.mkv`/`.mp4` bytes are fetched from the provider's CDN on demand). Exactly one provider is active per deployment, selected at startup by which token is set (`RD_API_TOKEN` or `TORBOX_API_KEY`).

Optionally, the library can be **driven by users' Trakt accounts** (SP2): when Trakt sync is configured, each enrolled user's watchlist and in-progress titles auto-acquire content, and a reconciler lifecycle-removes it. A title acquired from a watchlist is removed once it is un-watchlisted and nobody wants it (Trigger B; Trakt drops watched items from the watchlist). A title wanted only as in-progress is removed (Trigger A) only when every in-progress wanter has finished it and it is still wanted, which in practice means a show folded back in by the `REMOVE_FINISHED_SHOWS` finish-cleanup. A title still in `/sync/playback` never reads as finished, since the user is partway through it (a paused re-watch included). Trakt drops a finished title from `/sync/playback`, so an in-progress-only movie, or a show with `REMOVE_FINISHED_SHOWS` off, is kept after it is finished. Without Trakt nothing is acquired from watchlists or watch history, but the account mirror, dedup, the best-copy selection repoint and the daily upgrade engine still run over everything already in the account. `observe` also still deletes and blacklists any owned torrent Real-Debrid reports as `magnet_error`/`dead`/`error`/`virus` (mirror and `Manual` records included, provided the record has an IMDB id) and replaces it with a freshly scraped release when the record names a movie or an episode.

**Required environment variables:**
- A debrid provider token — exactly one of:
  - `RD_API_TOKEN` — Real-Debrid API token
  - `TORBOX_API_KEY` — TorBox API token

  Set one or the other, not both. Setting **both** is a startup error; setting **neither** is a startup error.
- `TMDB_API_KEY` — TMDB API key

**Optional:**
- `SCAN_INTERVAL_SECS` (default: 60, minimum: 10) — how often to poll the active debrid provider
- `DB_PATH` (default: `metadata.db`) — path to the redb database file
- `PORT` (default: 8080) — WebDAV server listen port
- `CDN_FIRST_READ_MB` (default: 8, clamped 2–16) — size (MB) of the FIRST read-ahead CDN fetch when a media file is opened. Front-loads the container header + early index so a player's open/ffprobe burst is served from one cold fetch instead of several round-trips (the dominant on-demand-streaming startup cost). Subsequent reads use the normal `BUFFER_SIZE` (2 MB) window. Set `2` to disable the enlargement (= prior behaviour). Wired via `DebridFileSystem::with_first_read_bytes`.
- `EPISODE_FILE_NAMES` (default: `canonical`) — how the VFS names episode files. `canonical` serves `Show (Year) - S01E02.mkv`, built from the episode the service reads the file as (see the `vfs.rs` row), so Kodi, Jellyfin and Plex read the same episode; Kodi's default rules otherwise read more episodes out of an episode title such as `Inside the Episode S2 E1`. `original` serves the torrents' own file names. A file the service can't number keeps its own name either way. Switching renames the library's episode files: every media server sees them as new files, and Kodi, which keys watched state by path, loses its watched marks unless it syncs them (e.g. through Trakt). Parsed by `config::parse_episode_file_names` (anything else falls back to `canonical` with a warning). Because the default is `canonical`, upgrading a deployment from a version without it renames its episode files once; set `EPISODE_FILE_NAMES=original` before upgrading to keep the old names. The database records the naming the VFS last served (`Store::served_episode_names`, a `meta` key; none recorded reads as original names), and a restart pre-populates the VFS in it (`tasks::prepopulate_vfs`), so the first scan after a change diffs every renamed folder and tells Jellyfin, then records the new naming.
- `RUST_LOG` (default: `info`) — log verbosity via a `tracing-subscriber` `EnvFilter` directive (the `env-filter` feature is enabled). Unset → `info` (unchanged behaviour); a malformed directive falls back to `info` rather than crashing startup. Scope it to this crate to avoid dependency noise, e.g. `RUST_LOG=debridmoviemapper=debug`, or target one module: `RUST_LOG=debridmoviemapper::acquire=debug,info`. Takes effect on (re)start. The acquisition lifecycle is instrumented for `debug`: `acquire` (scrape count, ranked top-3 with cached/resolution/source/seeders, the candidate added, idempotent/lapsed/NoAcceptableRelease outcomes), `observe` (per-tick reason a Pending torrent is still waiting — absent/no-files/selecting/downloading/probe-deferring — plus reaps at `warn` and `Verified` at `info`), `scraper` (candidate counts; never the token-bearing URL), and `tasks` (Trakt wanted-set sizes, reconcile op counts). `dav_fs` playback resolves log at `trace`, since they fire on every file open (e.g. `RUST_LOG=debridmoviemapper::dav_fs=trace`; never the CDN URL).
- `JELLYFIN_URL` — Jellyfin server URL (e.g. `http://jellyfin:8096`)
- `JELLYFIN_API_KEY` — Jellyfin API key
- `JELLYFIN_RCLONE_MOUNT_PATH` — rclone mount path as seen by Jellyfin (e.g. `/media`)

**Optional — Acquisition quality preferences (SP1):** (full descriptions in `README.md`'s env-var table)
- `MAX_RESOLUTION` (default: `1080`) — hard resolution ceiling for acquisition (`720`/`1080`/`2160`, each also accepted with a `p` suffix, or the `2160` synonyms `4k`/`uhd`); candidates above it are excluded.
- `AUDIO_LANGUAGE` (default: `original`) — required audio language: a 2-/3-letter ISO code or `original` (TMDB's original language **plus its listed `spoken_languages`** — any of them is acceptable, for both ranking and the probe; a title with no spoken languages listed behaves exactly as before, original only. An explicit ISO code ignores spoken languages entirely). A value that is not a language code (a full name, a locale, a 2-letter code `probe::is_known_language_code` doesn't know, `off`/`any`/`all`, or `und`/`mul`, which the probe knows but no parsed track carries: `config::NO_TRACK_CODES`) falls back to `original` with a warning. An unknown 3-letter code is used as written, with a warning (`config::parse_lang_code`), so a misspelt one gets every release rejected and blacklisted for 30 days. `no` is Norwegian and `na` is Nauruan; each is kept, with a warning that names the 3-letter code (`nor`, `nau`) to write instead (`config::MISREADABLE_CODES`).
- `SUBTITLE_LANGUAGE` (default: unset = `none`) — required subtitle language (ISO code), or `none`/`off`/unset to skip the check. Any other value goes through the same validation as `AUDIO_LANGUAGE`, and a rejected one falls back to `none`. A no-language code (`xx`/`zxx`, `probe::is_no_language`) is refused too and falls back to `none` with a warning (`SubReq::parse`). For the audio it turns the check off, but the probe's subtitle check has no such exemption, so taken as written it would reject and blacklist every release.
- `PREFER_HEVC` (default: `true`) / `PREFER_HDR` (default: `false`) — scoring preferences for HEVC and HDR/Dolby-Vision encodes.
- `STALL_TIMEOUT_SECS` (default: 1800, minimum: 60) — seconds without download progress before a Pending torrent is re-acquired.
- `MAX_ACQUIRE_ATTEMPTS` (default: 5, minimum: 1) — how many of the top-ranked candidates one acquisition pass tries to add, moving to the next only when the add itself fails (an add the provider reports busy, e.g. TorBox at its active-download limit, stops the acquisition instead; see the `acquire.rs` row). A release later rejected by `observe` (wrong title or audio, corrupt, stalled, dead) is blacklisted and the next-best candidate is tried, so over time every non-blacklisted candidate may be tried.
- `SCRAPER_ADDON_URL` (default: auto-templated from the provider token) — override the Torrentio/Stremio addon base URL. A pasted addon manifest URL (`…/manifest.json`) is accepted; `TorrentioScraper::build_base_url` drops the suffix.
- `SCRAPER_PROXY_URL` (default: unset) — route ONLY the scraper's traffic through an HTTP(S) proxy (a non-http(s) scheme is a startup error); CDN/TMDB/provider stay direct.
- `SCRAPER_MIN_INTERVAL_MS` (default: 1000, clamped 100–60000) — minimum spacing between scraper requests. Torrentio sends no rate-limit headers and answered 429 once ~80–100 requests arrived within a minute (the hourly episode check can scrape 100–200 episodes back to back), so every scrape is paced through the scraper's own `AdaptiveRateLimiter`; a 429 doubles the interval (honouring `Retry-After`) and is retried, up to 3 requests per scrape, before surfacing as the retriable error. Lower it for a self-hosted addon.

**Optional — Trakt sync (SP2):**
- `TRAKT_CLIENT_ID`, `TRAKT_CLIENT_SECRET` — both required to ENABLE Trakt sync (from a Trakt API app). If either is absent, Trakt sync is disabled (setting only one of them logs a warning naming the missing variable, e.g. `TRAKT_CLIENT_ID is set but TRAKT_CLIENT_SECRET is not; Trakt sync is disabled`) and nothing is acquired from watchlists or watch history (`observe` still deletes and blacklists a torrent Real-Debrid reports dead, and replaces it when its record names a movie or an episode). The scan loop's account mirror, best-copy selection repoint, same-hash duplicate deletion (always on) and dedup (dry-run by default) still run over everything already in the account, and so does the daily upgrade engine (on by default), which adds better cached releases and deletes the copies they replace, user-added torrents included. `UPGRADE_INTERVAL_SECS=0` stops that.
- `TRAKT_SYNC_INTERVAL_SECS` (default: 900, minimum: 60) — Trakt sync + reconcile cadence.
- `TRAKT_EPISODE_CHECK_INTERVAL_SECS` (default: 3600, minimum: 300) — episode-monitor cadence. (Note this exact env var name — it carries the `TRAKT_` prefix for consistency.)
- `TRAKT_CATCHUP_LOOKBACK` (default: unset = all-time) — **catch-up** lookback window. A show you've *watched* (not just watchlisted/in-progress) that Trakt reports as behind is auto-acquired, but only if you last watched it within this window: every aired regular episode not watched by all of its catch-up wanters (`reconcile_title` skips the intersection of their watched sets), including episodes that aired before the last watch. The default all-time window therefore covers every partly watched show in the user's whole history, which can be a large number of torrents. Accepts a number followed (optionally after spaces, case-insensitively) by a unit: `d`/`day`/`days`, `w`/`wk`/`week`/`weeks`, `m`/`mo`/`mon`/`month`/`months` (30 days; `m` is a month, not a minute) or `y`/`yr`/`year`/`years` (365 days), e.g. `90d`, `12w`, `6mo`, `6m`, `6 months`, `1y`; a bare number = days; `0`/unset = all-time (every watched show with unwatched aired episodes qualifies). Anchored on Trakt's per-show `last_watched_at`. Any other value is treated as all-time (logged at warn with examples of the accepted forms), never a startup failure. **Operational cost:** each catch-up candidate costs one Trakt `show_progress` call (plus a TMDB `show_status` call) per sync cycle, so an all-time window over a large watch history issues that many extra requests every `TRAKT_SYNC_INTERVAL_SECS` (the shared rate limiter paces them, so it's absorbed, not an error). Set a bounded lookback (e.g. `90d`/`6mo`) to scope the catch-up set — and the per-cycle API load — to recently-watched shows. **Note:** because it gates the shared per-show `show_progress` check, this window *also* scopes `REMOVE_FINISHED_SHOWS` finish-cleanup — a show last watched outside the window is not a finish-removal candidate (see that option).
- `TRAKT_ENROL_ALLOWED_HOSTS` (default: unset) — extra host names accepted in the `Host` header of the `/trakt` enrolment routes, on top of IP literals, `localhost`/`*.localhost`, single-label names and `.local`/`.lan`/`.internal`/`.home.arpa` names. Any other `Host` gets `421 Misdirected Request` (a DNS-rebinding guard, checked before the CSRF guard, for every method; a request with no `Host` header is allowed). A reverse proxy must also forward the browser's `Host` header unchanged, port included (nginx: `proxy_set_header Host $http_host;`). The CSRF guard compares it with the browser's `Origin` and evens out only a default port, so a rewritten Host gets every POST refused with 403. The guard's warn line logs the Origin, Host and Sec-Fetch-Site it compared. Parsed by `config::parse_allowed_hosts` into `TraktConfig.enrol_allowed_hosts`.

  Accounts are linked via the local-network enrolment page (`/trakt/accounts` on the WebDAV listener), not a static list.

**Optional — Upgrade engine (SP3):**
- `UPGRADE_INTERVAL_SECS` (default: 86400 = daily; `0`, or the boolean off-words `off`/`false`/`no`, disables; minimum 600 when non-zero; any other non-number keeps the daily default and warns that the engine is on, `config::parse_upgrade_interval`) — how often to run the quality-upgrade + full-season consolidation pass. On by default; set to `0` to disable entirely.
- `UPGRADE_BUDGET_PER_TICK` (default: unset = no cap, minimum: 1) — cap on the owned titles re-scored per upgrade pass. Unset, every pass visits every eligible title (see the `upgrade.rs` row for the titles it skips): measured on the live library (312 titles), that is ~490 scrapes (~8 min at the 1 s scraper pacing), up to ~2,300 only if every multi-episode pack's sample episode had a better single-episode release (a season pack listed under the sample's query doesn't count: phases (1) and (2) drop a stream whose name plainly names several episodes before ranking, `upgrade::is_pack_stream`, and one that only turns out to be a pack when staged is staged once and the rest of the pack is skipped). The default used to be 20, which put a full rotation at ~16 days, so a copy the pass would replace (e.g. an SD Russian-dub pack serving an English show's episode) waited up to two weeks for its turn. Either way titles needing attention go first (`upgrade::needs_attention`, judged on the copies still in the provider account: a `Verified` copy with no recorded quality, an unknown quality — `release::is_unknown_quality` — or `quality.unverified`), each group least-recently-checked first; under a cap they get half of it (rounded down) and the rest goes to the least-recently-checked remaining titles (`upgrade::upgrade_batch`), so attention titles that never find a better copy can't starve the others. A title with no copy left in the account is stamped and takes no slot.
- `UPGRADE_IDLE_SECS` (default: 300, minimum: 30) — seconds without a proxy read before a copy may be swapped, pruned or removed. The upgrade engine checks only the torrents a step changes (`ReadActivity::torrents_idle`): a swap or prune waits while a player has read, within the window, a torrent it deletes or takes an episode away from (`upgrade::copies_serving`: every owned copy of the affected episodes, or of the film, plus what their selection slots point at), and a title with a copy being read is skipped for that pass (cursor unchanged) while the pass moves on to the next title. It used to check the whole library, so on 2026-11-12 Jellyfin probing the file a swap had just added (about 75 s after the swap's notification) stopped the rest of the daily pass. Dedup removals, `execute_remove`, the scan loop's same-hash duplicate deletion and `selection::repoint_to_better_copies` still check the whole library (`all_idle`). **Start-up grace:** read activity is in-memory only, so right after a (re)start there is no read history — for the first `UPGRADE_IDLE_SECS` after the process starts the library counts as **not idle**, so every idle-gated deletion defers instead of firing on the first tick (a redeploy once deleted 81 torrents 34 s after start-up). The upgrade job therefore waits out the grace before its first pass (`scheduler::periodic_after` with `upgrade_first_run_delay`), rather than running a start-up pass that would defer every title and leave the next one a full `UPGRADE_INTERVAL_SECS` away (a service restarted at least daily would otherwise never upgrade).
- `ACQUIRE_DEAD_TIMEOUT_SECS` (default: 600, minimum: 120) — seconds an optimistically-added `Pending` torrent may remain unresolved before `observe` reaps it as dead, blacklists the hash, and re-scrapes.
- `DEDUP_REMOVE_DUPLICATES` (default: unset/`false`) — when `true`/`1`/`yes`/`on`, the duplicate-dedup pass actually **deletes** redundant torrents from the provider. Default is a **dry-run** that only logs the plan (`dedup: …` lines) so it can be reviewed first. Removal is additionally idle-gated (`UPGRADE_IDLE_SECS`, incl. its start-up grace) so it never interrupts an active stream. A copy is only ever removed in favour of copies of the **same or better quality** (quality first — resolution, then source tier, then checked before unchecked, an untagged axis counting as the lowest; see the `tasks.rs` row); pre-existing account-mirror copies get no protection. Only settled (`Verified`) copies take part — a `Pending` acquisition is neither removed nor allowed to displace one. A title with an owned record added within `UPGRADE_IDLE_SECS` (`tasks::fresh_dedup_groups`, e.g. an upgrade stage in flight) is left out of the plan, dry-run log included, until the window passes. This flag doesn't govern the scan loop's same-hash duplicate deletion, which is always on (see the `tasks.rs` row). Nor does the dry run keep several copies of a film: an adopted movie upgrade prunes every within-ceiling owned copy of the film (`upgrade::supersede_hashes`), editions and dubs under the same TMDB id included, whatever this flag says. Only `UPGRADE_INTERVAL_SECS=0` stops that.
- `REMOVE_FINISHED_SHOWS` (default: unset/`false`) — when `true`, a fully-watched **Ended** show that isn't watchlisted is auto-removed (Trigger-A finish cleanup), **including shows already in the library**. Default `false` only **logs** the finish-removal candidates (`trakt: <user> — N finished+ended owned show(s) would be removed (preview …)`) without removing — review the preview, then enable. (Mechanism: `sync_trakt` folds the finished+ended owned shows — those Trakt's per-show progress reports caught-up — into the wanted-set only when this is on, so the episode monitor's (`monitor_episodes`) Trigger-A finish removal fires on its next run (every `TRAKT_EPISODE_CHECK_INTERVAL_SECS`, idle-gated). Trigger A and the acquire-side guard are decided by `user_finished` over the **TMDB** aired set (regular episodes — Specials/season 0 are ignored, see `wanted::SPECIALS_SEASON`) against Trakt's per-episode watched set (read with `extended=progress` — without it every watched set was empty and nothing was ever finish-removed), so removal fires and the acquire path acquires nothing **when TMDB and Trakt agree on the aired episodes**; if TMDB lists an aired episode Trakt's watched set lacks, the show reads as not-fully-watched, is kept, and catch-up acquires that genuinely-unwatched episode — consistent, not a phantom acquire. A watchlisted show is never finish-removed. **Scoped by `TRAKT_CATCHUP_LOOKBACK`:** the finish-cleanup candidate set is built from the same per-show `show_progress` check that the catch-up lookback window bounds, so a bounded lookback *also* scopes finish-cleanup — a fully-watched Ended owned show last watched **outside** the window is neither previewed nor removed. This coupling is deliberate: decoupling it would reintroduce an unbounded per-cycle `show_progress` call for every owned watched show. With the default all-time lookback every finished+ended owned show is considered.)
- `ALLOW_RESOLUTION_DOWNGRADE` (default unset/`false`) — when `true`/`1`/`yes`/`on`, the upgrade engine may perform a **corrective downgrade**: when `MAX_RESOLUTION` is lowered below an owned copy, it replaces that above-ceiling copy with a ceiling-conforming CACHED release and prunes the higher-res copy (idle-gated, and only when such a replacement exists — a sole over-ceiling copy with no conforming cached release is kept). It applies to engine-acquired copies (acquired under a previously-higher ceiling) and pre-existing account-mirror copies alike: a mirrored over-ceiling file has its real resolution recorded (older mirror records stored `quality: None` and are re-derived from their file names — see the account-mirror note), so it is **never treated as unknown-lowest quality** — replacing it is always this gated corrective downgrade. Default is a **dry-run** that only logs the planned downgrades (`upgrade: … would downgrade …`). Pure quality upgrades are unaffected by this flag. For a movie or a singleton episode it never goes below a within-ceiling resolution the title already owns, a copy whose source is untagged included (`upgrade::within_ceiling_floor`): owning a 2160p copy and an untagged 1080p copy under a 1080p ceiling, only a cached 1080p release replaces them, never a 720p one. An over-ceiling season pack (`correct_over_ceiling_packs`) has no such floor: it is replaced by the best cached within-ceiling pack covering its episodes, whatever else the show owns. Only the old pack is pruned, and the scan loop's selection repoint then moves a slot to any better within-ceiling copy the show already owns for that episode. An over-ceiling pack holding a video file with no episode code that its record doesn't account for (`upgrade::copies_holding_codeless_files`) is not corrected at all: pack correction skips it before scraping, since keeping it beside a replacement would stage another pack on every visit. A pack the engine acquired whose record maps that file to an episode in its `provides` (`vfs::codeless_episode_files`, e.g. `Season 04/E09 - Title.mkv` under an explicit season) is corrected like any other.

## Architecture

The project is structured as both a binary (`main.rs`) and a library (`mapper.rs` as lib root).

**Background tasks (the scheduler model, SP2):** `main.rs` spawns `scheduler::run`, which spins up cooperating independent jobs over the shared `AppState`. The Trakt/episode/upgrade jobs are each driven by the `scheduler::periodic` primitive (run immediately, then `interval` after each tick completes — a fixed-DELAY cadence — until shutdown; the upgrade job uses `periodic_after`, whose first run waits out the read-activity start-up grace); the scan loop instead runs under `supervise` with its own internal cadence and shutdown-aware awaits:
- **Scan loop** = `run_scan_loop` (behaviour-preserving): it loads the persisted matches, pre-populates the VFS from them (in the episode naming the previous process served, `prepopulate_vfs`) and then calls `scan_tick` every `SCAN_INTERVAL_SECS` (the tests drive `scan_tick` directly). On a prune tick the blacklist and `upgrade_checks` cursor prune runs first. One tick then fetches one provider listing (a re-acquisition `observe` triggers fetches its own) and runs, in order: acquisition verification (`engine.observe`), the staging sweep (`upgrade::sweep_staging_intents`), the same-hash duplicate deletion (`dedup_torrents_by_hash`), the re-fetch of cached identifications that list no video file (`refresh_fileless_infos`: 5 min after a torrent is first noticed, then hourly, at most 10 per tick), identification of new torrents via TMDB + `update_vfs`, `record_mirror_owned`, `dedup_owned`, `selection::repoint_to_better_copies`, and the daily maintenance (the mirror reaper and `backfill_missing_imdb_ids`). A suspect empty listing stops the tick after `observe`. See the `tasks.rs` row. Implemented in `tasks.rs`.
- **Trakt cycle** = `sync_trakt` then `reconcile_wanted` (sequentially, so the reconciler sees the just-synced wanted set), every `TRAKT_SYNC_INTERVAL_SECS`. Spawned **only** when Trakt is configured.
- **Episode monitor** = `monitor_episodes` (every `TRAKT_EPISODE_CHECK_INTERVAL_SECS`). Spawned only when Trakt is configured.
- **Upgrade job** = `run_upgrade_once` (every `UPGRADE_INTERVAL_SECS`, default 86400s/daily, the first pass once the `UPGRADE_IDLE_SECS` start-up grace is over; gated on `UPGRADE_INTERVAL_SECS > 0`): re-scores every eligible owned title (not a `Manual` one, nor one whose representative record is still `Pending`; a title with no owned copy left in the provider listing is skipped with its cursor stamped and takes no budget slot, and a title with a copy being read is skipped for that pass with its cursor unchanged; see the `upgrade.rs` row) (copies of unknown or unchecked quality first; `UPGRADE_BUDGET_PER_TICK` caps it) — including **unknown-quality** copies (no recorded quality, or an untagged resolution/source tier), which rank lowest and are replaced by any known-quality cached within-ceiling release that passes the probe, at or above the copy's resolution when that is tagged (a known resolution stays a floor) — stages meaningfully-better CACHED releases (trying ranked candidates in order until one is usable — in-tick fall-through, like the pack/consolidation paths), and performs a swap of the `selection` (held back while a player reads a copy it changes) + prune of the superseded torrents (for a movie, every within-ceiling owned copy of the film, `upgrade::supersede_hashes`, and an over-ceiling one too only with `ALLOW_RESOLUTION_DOWNGRADE` on; for shows: per singleton episode, and per episode served from a within-ceiling multi-episode pack); also consolidates scattered per-episode torrents into full-season cached packs (no quality regression). Disable by setting `UPGRADE_INTERVAL_SECS=0`. Implemented in `upgrade.rs`.

The Trakt cycle + episode monitor are gated on `scheduler::trakt_jobs_enabled` (a Trakt client **and** `config.trakt` both present); otherwise only the scan loop and (unless `UPGRADE_INTERVAL_SECS=0`) the upgrade job run. Nothing is acquired from Trakt then, but both still act on everything already in the account (mirror, dedup, selection repoint, same-hash duplicate deletion, upgrade swaps and prunes, and `observe`'s dead-status reap, which replaces the release when its record names a movie or an episode). The local-network Trakt enrolment routes (`/trakt/accounts`) are served on the existing WebDAV listener.

**On-demand (synchronous, during WebDAV file reads):**
- **Repair:** Triggered when a media file is read and `provider.resolve_url` returns `AppError::Unavailable` (RD maps every unrestrict failure except a 401/403 or a 429 to it: a 5xx, a transport failure, a stale-link 4xx such as 404, or a missing link), **or** when the CDN returns a persistent **5xx** on the byte fetch (the file resolved but is broken on the provider, not just a stale URL — once the first fetch and its same-URL retry (no re-resolve) both 5xx (a 5xx that follows another failure, a connection or body error or a stale-URL re-resolve, is retried once on the same URL; if that retry 5xxs too, the read fails without a repair, since no attempt is left for a repaired URL, and the next read can still escalate), the byte-fetch path escalates to the same instant repair, once per read, bounded by the repair cooldown). For cached torrents, repair completes inline (~1-2s delay); for non-cached torrents, the file fails and a new torrent is left to download. A persistent 5xx is no longer an endless player retry-storm. A 429 on resolve fails the read without repair. The whole inline repair is bounded to 30 s (`repair::INSTANT_REPAIR_TIMEOUT`): its provider calls use the background retry budgets, so during an outage it could otherwise hold the read for minutes. A timed-out repair returns `RepairFailure::Deferred` and leaves the torrent visible with its attempt budget reset and its 30 s cooldown restarted when the repair is abandoned (`RepairManager::note_abandoned_repair`; the timeout equals the cooldown, so a cooldown counted from the start would already be over and the next read would run another 30 s repair at once). So does a repair cut short by a dropped read. In either case a new-id torrent the repair added but had not adopted is deleted in the background.

| `main.rs` | Initializes shared state, spawns the scheduler (`scheduler::run`, which runs the scan loop + the Trakt/episode/upgrade jobs), starts the WebDAV server on `PORT` (default 8080), listening on every interface (`0.0.0.0`; there is no bind-address setting). Before anything else, `--healthcheck` included, it loads `.env` through dotenvy. If a `.env` exists but can't be loaded (a line dotenvy can't parse, such as an unquoted value containing a space, or a read error), it prints a `Configuration error` to stderr and exits 1 (`config::load_dotenv`, whose `dotenv_failure` builds the message). dotenvy stops at the first bad line, so every later setting would otherwise silently take its default. Connections are bounded by a `MAX_CONNECTIONS` (256) semaphore, and `http1::Builder` sets a `header_read_timeout` (60s) so an idle/dead keep-alive connection can't pin its permit indefinitely (a dead peer would otherwise leak permits until the pool exhausts and the service silently rejects all new connections). The `header_read_timeout` only bounds the HEADER phase, so a peer that dies uncleanly while its connection is **idle** (between range requests, or on a half-open keep-alive slot; no FIN/RST) is reclaimed by **TCP keepalive** (`set_tcp_keepalive`: 60s idle + 3×10s probes ≈ 90s) applied to every accepted socket — otherwise it would pin its permit until the OS retransmission timeout (minutes). (A peer that dies *while* body bytes are being written is reclaimed by the retransmission timer instead — Linux only probes a socket with no unacknowledged data in flight — but the proxy sits idle between its many small range requests, so keepalive covers the dominant case.) Active streams are unaffected (a live peer answers the probes). `--healthcheck` mode issues a real `OPTIONS /` HTTP request (not a bare TCP connect) and requires an HTTP status line within 5s, so a dead or hung accept/handler path reports UNHEALTHY. A saturated connection pool answers 503 and so reads HEALTHY by design (busy, not wedged; an orchestrator acting on health, such as Swarm, Kubernetes or an autoheal sidecar, would otherwise restart it and kill every stream); only when the 503-rejecter pool is also exhausted (the connection is dropped) does it read unhealthy. Plain Docker/Compose never restart an unhealthy container (`restart:` policies act only on exit): with the shipped compose.yml the health status only gates `depends_on: service_healthy` at start-up, so a wedged server stays wedged until someone intervenes. `header_read_timeout` plus TCP keepalive are what bound permit leaks. Benign connection errors (client disconnects, our own header-read timeout) are classified by `is_benign_connection_error` (io-kind source check, then the `dbg_is_ignorable_disconnect` Debug-string fallback) and dropped silently; `real_header_read_timeout_is_classified_ignorable` drives a real hyper timeout through that same function. Dedup never consults `MAX_RESOLUTION` (a copy above it is never ranked down for it), so it never trades resolution down (a corrective downgrade stays the upgrade engine's job under `ALLOW_RESOLUTION_DOWNGRADE`). Nor does a collection take the film's keep slot. The keep is the best single-film copy, so a collection, whose record quality is its largest file's and possibly another film's, never makes a single copy redundant. Accepted consequence of no mirror protection: when a mirror copy loses to a better engine copy, the title's survival rests on that engine copy, which Trigger A/B may later remove (the lifecycle's own mirror protection — `removal_hashes`/`engine_hashes` — is unchanged). A title with an owned record added within `UPGRADE_IDLE_SECS` (`fresh_dedup_groups`: an upgrade swap may be in flight) is left out of the plan, dry-run log included, until the window passes. Where dedup prefers the old copy it would otherwise delete the just-staged one while the swap prunes the old one, losing both: a corrective downgrade, an over-ceiling pack correction, or a consolidation pack of equal quality rank but a lower score than the singles it covers. Dry-run by default; `DEDUP_REMOVE_DUPLICATES=true` enables idle-gated deletion + owned-record/selection cleanup (`Store::forget_owned`)). A listed `downloaded` torrent whose cached identification lists no emittable video file (TorBox can report a finished torrent with `files: null`, and the identification is otherwise fetched once per id) has its files fetched again by `refresh_fileless_infos`, before new torrents are identified. The first fetch comes `FIRST_INFO_REFRESH_AFTER` (5 min) after the scan loop first notices the torrent (the schedule is in memory, so a restart notices them all again), then again `INFO_REFRESH_AFTER` (1 h) after every fetch that fails or still finds none, at most `MAX_INFO_REFRESHES_PER_TICK` (10) per tick. An engine copy keeps its authoritative identification. A cached list with files is never swapped for an empty one. Before identifying anything, the scan loop runs two passes over the listing. With no such intent this costs one store read. It deletes the torrent of each abandoned intent whose hash is not owned, and closes an intent whose hash is owned without deleting anything. An intent whose hash is not listed is closed only once deleting its recorded torrent id succeeds, or once it is `STAGING_LISTING_LAG_SECS` (10 min) old, so a lagging TorBox listing cannot let the mirror adopt the torrent. Deleted torrents are dropped from the tick's listing. It is not idle-gated. A listed torrent whose intent was open when the tick started (read before the listing) or is still open after the sweep, and whose hash isn't yet recorded as owned with an authoritative entry (`staging_unrecorded`: a candidate being staged or acquired, one whose rejection delete failed, or one the upgrade job discarded while `observe` ran), is kept out of the tick's VFS, identification and mirror. Then the same-hash duplicate deletion (`dedup_torrents_by_hash`) keeps the first `downloaded` torrent listed per hash (the newest) and deletes the other `downloaded` torrents with that hash. It is always on, not governed by `DEDUP_REMOVE_DUPLICATES`, and gated on `all_idle`; a torrent id listed twice in one listing (a page-boundary repeat) is skipped, never deleted; both provider clients already drop such repeats (`rd_client::drop_repeated_ids`), so this skip is a second guard. On start-up and on every daily prune tick, before it fetches the listing, the scan loop drops blacklist entries older than 30 days (`Store::prune_blacklist_before`) and the `upgrade_checks` cursor rows of titles no longer owned (`Store::prune_upgrade_checks_not_owned`). On the first trusted listing on or after the daily prune tick (`ScanState::maintenance_due`, so a failed or suspect listing on that tick does not postpone it a day), `backfill_missing_imdb_ids` fills the empty `imdb_id` of present `Verified` owned records (written by the mirror when TMDB `external_ids` failed transiently) via the atomic `Store::set_imdb_id_if_empty`: one lookup per title per pass, and a transient failure ends the pass. A multi-film collection (`tasks::multi_feature_hashes`) is never upgraded by the movie path: `try_upgrade_movie` returns `NoChange` before scraping. **Shows** get the same treatment at four layered stages per tick: (1) **per-episode** upgrade/downgrade — every owned singleton episode is re-scored and swapped independently, against the better (`best_owned_quality`) of the singleton's own quality and the owned copy its slot currently serves, since the swap repoints that slot (so a slot served by a better pack is never moved to a candidate that beats only the singleton; the baseline also counts a copy adopted for the same slot earlier in the tick); (2) **pack-served episode upgrade** (phase a2) — for every owned **within-ceiling** multi-episode pack (`provides.len() > 1`; a pack with no recorded quality counts as unknown on both axes), each episode whose `selection` slot points at the pack is re-scored against the **pack's** quality and, on a better cached **true singleton** that is also no regression vs the pack on either axis (`pack_split_no_regression`: candidate source tier AND resolution ≥ the pack's — the per-axis test `consolidation_target` applies, filtered before the sample-first check, so a pack is never split into singles below it on either axis; an UNKNOWN pack axis (0) is the lowest, so any known candidate passes it. No pass undoes another: (1) and (2) only ever move a verified copy UP a category (`is_target_improvement`: a higher resolution, or a higher tier at the same resolution; only the one-shot unverified rule can do otherwise, and every adopted copy is verified), so singles (2) split from a pack — at least the pack on both axes, above it on one — never come back down to where (4)'s no-regression gate could re-adopt that pack. Before the same-resolution tier rule, (1) swapped the BluRay x264 singles split from a WEB x264 pack for higher-scoring WEB x265 ones and (4) folded those back into the pack, every two visits; an equal-tier/resolution split can only come from the unverified rule, and (4) re-adopts a pack only on a probe `Pass`, recording it verified, so such a pack is split + folded back at most once), swapped exactly like (1) (same stage/probe/idle-gated `apply_upgrade` path — phases (1) and (2) share `upgrade_episode_slot`, differing only in `EpisodeSupersede`: a singleton is pruned outright, a pack only via `pack_prunable_after_repoint`). The pack is **pruned only on the repoint that leaves it serving no slot AND with every episode it provides held by another `Verified` owned record of the show whose torrent is still PRESENT** — `other_owned_coverage` re-reads the store just before the swap (so singles staged/pruned — or an overlapping pack pruned — earlier the same tick count, and a `Pending` copy, still reapable, does not), and the decision itself (`PrunePlan::Pack` → `PackPrune::resolve`) is settled inside `apply_upgrade` against the provider listing it fetches before its final read check: a `Verified`-but-absent (lapsed) record does not count (the VFS falls back to the pack for that record's stale-selection episode, so deleting the pack would lose the episode with nothing to bring it back — no file left to read for on-read repair), while a single adopted earlier the same tick counts as present even before the listing shows its add (`EpisodeTick::adopted`); otherwise the pack is kept. Only selection-served episodes are considered (a mirror pack with no managed selection is left alone; the selection pass gives a mirror pack's episodes slots when another present copy also holds them, `selection::plan_missing_episode_slots`, and from then on they count as served, so such a pack can be split and pruned like an engine one). No show swap prunes a copy holding a video file with no episode code that its record doesn't account for (`copies_holding_codeless_files`; a code-less file that `vfs::codeless_episode_files` maps to an episode in the record's `provides`, as in an engine copy of an absolute-numbered single or of a code-less pack under an explicit season, is accounted for, so such a copy is pruned like any other. It reads the persisted identifications only when a prune is at hand; a copy with no persisted identification is judged by its record): phases (1) and (2) move the slot and keep the old singleton or pack, consolidation leaves such a copy out of `superseded` (it is not pruned and doesn't count for the new pack's provenance), and pack correction (3) skips such an over-ceiling pack before scraping, since keeping it beside a replacement would stage another pack on every visit. Sample-first cost bound: if the pack's first served episode yields no improving candidate (or its scrape fails), the rest of that pack is skipped this visit; and phases (1) and (2) drop, before ranking, every stream whose torrent name plainly names several episodes (`is_pack_stream`: an episode range, two or more episode codes, or a season token such as `S01`, `Season 2` or `S01-S03` with no episode code, no episode word (`E05`/`Ep 5`/`Episode 12`) and no trailing ` - NN` number), so a season pack named as one is never staged by the per-episode phases. A candidate that stages as no single anyway (a multi-episode torrent whose name doesn't say so, such as `Show Complete Series`, or one with no file that maps to an episode, such as a multi-file pack of absolute-numbered `Show - 05.mkv` files with no explicit season; per-episode staging reads episodes as acquisition does, `vfs::show_episode_files`, so a single-file absolute-numbered release is a single and is adopted) is staged at most once per show tick (`EpisodeTick::not_singles`, shared with (1): Torrentio lists the same season pack under every episode query and the per-episode path never adopts one), not once per served episode. From then on it counts as no improving candidate, so a pack whose sample episode improves only on such torrents is skipped the same way: one scrape and at most one staging. A hash adopted earlier the tick is never re-staged either. Over-ceiling packs are left to (3). Dedup cooperates: its second sweep removes a copy only in favour of same-or-better-quality coverage, so when a kept pack is the sole holder of some episode the better singles it also covers are kept (the quality-agnostic sweep that used to delete them — the 2026-11-11 regression — is gone). This is what replaces an air-date grab like an SD foreign-dub pack serving one episode of an otherwise-1080p season; a lower-quality full-season pack may be split into better singles, which (4) later folds back into a pack only when one at least as good on tier and resolution exists (never the split pack itself, bar the one unverified re-fold above); (3) **over-ceiling pack correction** (`correct_over_ceiling_packs`) — an owned season pack above the ceiling is replaced by the best within-ceiling CACHED pack covering the same episodes, with no `within_ceiling_floor` (the selection repoint later moves a slot to a better within-ceiling copy the show owns; see `ALLOW_RESOLUTION_DOWNGRADE`) (it repoints only the slots the old pack served, or that have no selection, so a slot serving another copy keeps it, and records the replacement's `provides` as every episode it holds; same downgrade gate; a sole over-ceiling pack with no conforming replacement is kept, never deleted; its candidates exclude every hash the show owns at that point — re-read from the store, so a single adopted by (1)/(2) earlier the tick is never re-staged and then, on TorBox whose re-add returns the SAME torrent id, deleted by the coverage-miss cleanup); (4) **full-season consolidation** (`consolidation_target`; a show with no season that has a single-episode record and at least two records supplying it (packs included, `season_has_scatter`), e.g. one held only as packs, skips the TMDB aired-episode lookup; the injected lookup returns `tasks::AiredEpisodes`, and a complete lookup listing no aired regular episode is `NoChange`, cursor stamped, while only a failed lookup that found nothing defers) — scattered per-episode torrents are merged into a CACHED full-season pack covering every aired episode at same-or-better quality (its tier/resolution no-regression half, `pack_no_regression`, is checked before staging too, so a candidate below an owned episode is never added just to be deleted; an unknown axis — 0, or no recorded quality — is the lowest on either side: an owned episode's unknown axis never blocks a pack, a pack's unknown axis is a regression against any known episode axis). A copy adopted earlier in the same visit by (1), (2) or (3) (`ShowEpisodePass::adopted`: its hash and the torrent id its add returned) counts as present even while a lagging TorBox listing doesn't show it yet. When consolidation folds it into the pack, it is deleted by that id (`prune_behind_staged` → `prune_owned_hash_in`), and its records are dropped only once that delete succeeds. A single-episode stream (one episode code and no episode range in the torrent name, or no code but a trailing ` - NN` number (`[Group] Show - 05 (1080p)`; a batch `- 01-12` has none), the torrent name being the first line of the stream description: `is_single_episode_stream`, which treats the range names `S01E01-E10`, `S01E01-10`, `S01E01-S01E10` and `S01E01~E10` as packs. The `NxM` and separated ranges (`1x01-10`, `1x01-1x10`, `S01.E01-E10`) count as packs too, since `parse_se_all` leaves them undecoded or reads both endpoints; `EPISODE_RANGE_RE` itself covers only the contiguous `SxxEyy` form) is never staged as a pack, here or in pack correction (both rank through `rank_cached_pack_candidates`), and a candidate that staged and turned out multi-season or missing an aired episode is remembered for the process's life (`NOT_SEASON_PACKS`, per `AppState`, kept out of the acquisition blacklist) and not staged again. Consolidation is never a downgrade path — it never trades quality. **Unknown quality = lowest everywhere** (`release::is_unknown_quality` / `quality_rank`): an owned copy with no recorded quality (baselined as `QualitySummary::unknown()`) or an untagged resolution/source tier is improved by any known-quality cached within-ceiling candidate that passes the probe, at or above its resolution when that is tagged (a known resolution stays a floor, so this ungated path never trades resolution down; movie baseline `best_owned_quality` = known before unknown, then `effective_score`, except that an unknown within-ceiling copy at a higher resolution than that pick baselines instead; per-episode singleton; pack-served (2); consolidation), never by an unknown one, and a known copy within the ceiling is never "improved" by an unknown candidate — the swap records the adopted release's known quality, so a second visit changes nothing (converges). **Hard constraint:** a copy whose file name shows a resolution **above** `MAX_RESOLUTION` is never unknown-lowest, whatever its source tier — `is_unknown_quality` exempts an over-ceiling resolution, `run_upgrade_once` first re-derives any `quality: None` record's quality from the persisted identifications, and heals an account-mirror record whose untagged resolution or source tier its file names now tag (`tasks::backfill_owned_quality`, run on every pass), and mirror records now store an over-ceiling file's real resolution (`QualitySummary::of_owned`) — so it stays under the corrective-downgrade rules and `ALLOW_RESOLUTION_DOWNGRADE`. A mirror record (`Verified`, empty provenance, no quality, no `provides`) whose listed torrent lists no video file is dropped by the scan loop's mirror pass and mirrored again once its files are back. **Data flow for playback:**
1. Jellyfin/player opens a media file via WebDAV
2. `dav_fs.rs` resolves the file's `FileLocator` to a CDN URL via `provider.resolve_url(&FileLocator)` (cached). Real-Debrid resolves via the locator's restricted `link` (1h cache); TorBox resolves by `(torrent_id, file_id)` via `requestdl` (no per-file link; ~3h cache).
3. `ProxiedMediaFile` fetches bytes from the CDN URL with a 2MB read-ahead buffer (the FIRST fetch per open uses the larger `CDN_FIRST_READ_MB` window) and serves them to the player. A bounded `206` body is read to its natural end so reqwest returns the TCP+TLS connection to the keep-alive pool — the next window reuses it instead of re-handshaking; a Range-ignoring `200` (whole-object) is still read window-bounded then dropped (we can't drain gigabytes).

**Persistence:** Embedded `redb` database (`metadata.db`), created automatically on first run. Some tables can be rebuilt: `matches` (the TMDB identification cache), `blacklist` (TTL'd; losing it only lets rejected releases be tried again), `upgrade_checks` (the upgrade cursor), `wanted` (rebuilt by the next Trakt sync) and `staging` (open staging intents of upgrade candidates and acquisitions; losing it only forgets adds cut off before they were checked or recorded, which the account mirror may then adopt). The rest are authoritative and exist nowhere else: `owned_hashes` (provenance, `provides`, quality), `authoritative_ids`, `selection` and `trakt_tokens`. Deleting the file loses every Trakt enrolment and the lifecycle provenance: engine copies are re-adopted as empty-provenance mirror records that the Trigger A/B lifecycle won't remove, and managed selections fall back to the VFS default. All `redb` access goes through `store.rs` (the `Store` type); modules never open transactions inline.

## Key Design Decisions

- **Provider abstraction:** All components depend on `Arc<dyn DebridProvider>` (defined in `provider.rs`) rather than a concrete client. `RealDebridClient` and `TorBoxClient` are the two implementations; exactly one provider is active per deployment, chosen at startup by `choose_provider` based on which token (`RD_API_TOKEN` or `TORBOX_API_KEY`) is set.
- **TorBox specifics:** TorBox lists torrents (with files inline) via `mylist`, resolves a file by `(torrent_id, file_id)` via `requestdl` (so `FileLocator.link` is `None`), re-adds by hash via `createtorrent`, deletes via `controltorrent`, and treats `select_files` as a no-op (TorBox auto-selects). A finished download is normalised to `status = "downloaded"` even when its cache has lapsed (TorBox keeps such entries listed as Inactive), so owned-but-uncached films still appear in the library and re-acquire on playback. `mylist?id=` (the single-torrent `get_torrent_info`) can answer a spurious 404 ("No torrents found for this user") for a torrent that exists, so every upgrade staging site looks a freshly-added candidate up through `upgrade::staged_torrent_info`, which retries a 404 after 1, 2, 4 and 8 s (other errors return at once), while `await_downloaded` simply re-polls. The on-read instant repair retries a 404 on its three lookups too, on a shorter 0.5 s / 1 s schedule (`provider::torrent_info_retrying_not_found` with `repair::REPAIR_INFO_NOT_FOUND_BACKOFF`), since the read is waiting. TorBox's `progress` (a `0.0–1.0` fraction) is mapped to the canonical `Torrent.progress` as a `0–100` percentage (matching Real-Debrid) so the acquisition engine's stall detector — which resets only on a progress *change* — sees a moving signal for an actively-downloading uncached torrent (without it, `progress` stayed a constant `0.0` and a legitimate download was falsely reaped + blacklisted after `STALL_TIMEOUT_SECS`). The `mylist` response is parsed defensively: per-torrent fields TorBox sends loosely — `size: -1` (metadata not yet resolved) and `files: null` — are tolerated (signed sizes clamped to 0, null fields defaulted) so one malformed entry cannot fail the whole decode and hide the entire library. A torrent, file, `createtorrent` or queued id, or a size, sent as a numeric JSON string is read as the number (`lenient_int`), and so is a stringized progress (`lenient_f64`), and a `mylist` listing in which every entry has an unusable id or hash is refused as an `Err` (the tick is skipped, as for any failed listing) rather than returned as an empty account, which the scan loop would trust after 10 minutes. An add TorBox queues because the account is at its active-download limit is deleted from the queue and fails as provider-busy, so `acquire` retries later instead of queueing more candidates (see the `torbox_client.rs` row).
- **Provider-neutral file resolution:** The VFS stores a `FileLocator { hash, torrent_id, file_id, file_path, link }` per media file rather than a raw RD link. `resolve_url(&FileLocator) -> Result<String, AppError>` is the single resolution primitive (and `invalidate(&FileLocator)` drops a cached resolution); RD resolves via the locator's restricted `link` (keeping its old unrestrict/cache logic as private inherent methods), while `(torrent_id, file_id)` is used by providers without per-file links (TorBox). `AppError::Unavailable` is the provider-neutral "bytes not currently available → re-acquire/repair" signal — RD maps every unrestrict failure except a 401/403 or a 429 to it (a 5xx, a transport-level failure (timeout/connect, no HTTP status), a stale-link 4xx such as 404, or a missing link), and `dav_fs` drives instant repair off `Unavailable` rather than inspecting an HTTP status.
- **Static linking / scratch Docker image:** The Dockerfile builds with musl targets (`x86_64-unknown-linux-musl`, `aarch64-unknown-linux-musl`) producing a minimal final image on `scratch`. The runtime image's `/etc/ssl/certs/ca-certificates.crt` is unused today (reqwest's `rustls-tls` trusts the compiled-in webpki-roots); it is copied only so a later switch to native roots keeps working on scratch.
- **Adaptive rate limiting:** An `AdaptiveRateLimiter` (token bucket, capacity 1, in `ratelimit.rs`) is shared across a provider's API calls — both `RealDebridClient` and `TorBoxClient` use it. Baseline: Real-Debrid 250 ms (4 req/s; RD documents 250 requests/minute and sends no rate-limit headers, so steady pacing is its only proactive control), TorBox 100 ms (10 req/s). On 429: interval doubles (max 30s under sustained throttling) and `Retry-After` is respected. On success: interval **halves** toward baseline (multiplicative recovery, never below the client's baseline) so a bulk throttle burst doesn't leave later requests crawling at the raised ceiling. **TorBox additionally paces proactively:** `send_data`/`send_ok` read `x-ratelimit-remaining`/`-reset` from every response and call `observe_rate_limit`, holding the next request until the window resets when it is nearly spent — so bulk acquisition stays under TorBox's ~60/window `createtorrent` limit instead of storming into 429s. Real-Debrid sends no rate-limit headers (confirmed live), so it stays on the reactive MIMD path (multiplicative-increase on 429, multiplicative-decrease on success — see `ratelimit.rs`). RD signals throttle as a bare `429` (`error_code 34`, no `Retry-After`); separately, **any 5xx** on `unrestrict/link` (503 is RD's `hoster_unavailable`, `error_code 19`; 500/502/504 are infra errors) is a terminal status (no retry) — this is the synchronous on-read playback path, so it must fail fast rather than run the full ~10-attempt backoff (~3 min) that would surface to the player as a hang. The same path also uses a **small bounded retry budget (3, via `fetch_with_retry_n`)** plus a **10s `connect_timeout`** (separate from the 60s request timeout) so a transport-level hang (timeout/connect) can't stall a WebDAV read for the full ~10×60s window — a dead connect fails over to repair in ~30s instead. Both read-path calls (RD `unrestrict/link`, TorBox `requestdl`) also set a 15 s per-request timeout (`provider::READ_PATH_REQUEST_TIMEOUT`) in place of the clients' 60 s, so an endpoint that accepts the connection and never answers costs 3 × 15 s, not 3 minutes. `resolve_url` maps a 5xx, a transport-level failure (no HTTP status), **and a stale/expired-link 4xx such as 404** (recoverable by a re-add-by-hash) to `AppError::Unavailable` → on-demand repair; a permanent auth 4xx (401/403 bad token) and a 429 that outlasts the 3-attempt read budget stay a hard `Http` error that fails the read without repair (`unrestrict_status_skips_repair`, mirrored by TorBox's `requestdl_status_skips_repair`): a re-add can't fix a bad token, and throttling says nothing about whether the bytes exist, so repairing would re-add (on RD, delete) a healthy torrent inside the throttled window. Note the fast-fail budget bounds the *attempt count and connect phase*, NOT the shared limiter's pre-request wait: since one `AdaptiveRateLimiter` is shared across a provider's calls, under **sustained** throttling a parked `next_allowed` (bounded by `MAX_RETRY_AFTER_SECS` = 300s, and for TorBox by `observe_rate_limit`) can add backpressure latency to an on-read `resolve_url` too. This is deliberate backpressure (a heavily-throttled provider genuinely can't serve the bytes yet) rather than a bug, and is bounded; a dedicated read-path limiter would trade it for a higher 429 rate against the provider.
- **Per-client retry helpers:** `rd_client.rs` has `fetch_with_retry(make_request, terminal_statuses)` (default 10-attempt budget) which delegates to `fetch_with_retry_n(make_request, terminal_statuses, max_attempts)` — callers pass the status codes that should abort without retrying (e.g. 404 for `get_torrent_info`, the full 5xx set — 500/502/503/504 — for `unrestrict_link` so the playback resolve path fails fast to repair). `unrestrict_link` uses `fetch_with_retry_n(.., 3)` (a small budget) so a transport-level hang can't stall a WebDAV read for the full ~10×60s window. A 2xx whose body breaks off mid-read (a reset, a body cut short of its Content-Length, the request timeout firing while it streams) is retried like a statusless transport error (100 ms·attempt backoff, capped at 1 s). With the budget spent, the body error itself is returned (no status, so `resolve_url` maps it to `Unavailable`), not the synthetic decode-failure 502. `torbox_client.rs` has `send_data`/`send_ok`, which rate-limit, retry on 429/transient errors (including a body that breaks off mid-read or a 200 body that fails to decode), and unwrap TorBox's `{success, detail, data}` envelope.
- **Identification scoring:** `identification.rs` cleans filenames extensively before TMDB lookup. A ` - NN` episode number that ends the name (the anime form `Show - 12 (1080p)`, `Show.Name - 101`, optionally `Ep`-prefixed or `v2`-suffixed, never a 19xx/20xx year, a single digit, or a number followed by a bracketed release year: `Prefix - 21 (2008)` is a numeric film title, kept with its year) and an `Ep01`/`Ep 5` marker end the title, so the episode number never reaches the TMDB query. Shows vs. movies are guessed from file structure (`is_show_guess`): an episode marker (SxxEyy, NxM, `Season N`, the trailing ` - NN` / ` - EpNN` episode number `trailing_episode_number` reads, as in `[Group] Show - 12 (1080p).mkv`, …) in any selected file name makes it a show, otherwise more than one selected video of at least 100 MB does, so a sample or extra doesn't count. Names are tried in order (`identification_names`): the largest selected video file's name when it names a title of its own (`names_a_title`), else its nearest folder that names one, else the torrent name (`identification_name`, shared with the acquisition title check); then the torrent name; then the file name. A file name with no title of its own (`S04E09 - Episode Title.mkv`) is searched last because what `clean_name` leaves of it is the episode title. A match cached under the earlier first-name rule stays until its `matches` entry is dropped (the torrent leaves the account). A short all-digit title that comes with a release year (`9.2009.1080p.BluRay.mkv`) is searched (`is_generic_title_given_year`), and the short-title rule accepts only an exact title of that year; a bare `1.mkv` stays generic. `Series N`, `Staffel N`, `Stagione N`, `Sezon N`, `Seizoen N`, `Temporada N` and `Saison N` open no title, nor does `Season One` (`LEADING_NUMBERING_RE`), and a name that is only `Series N`, `Staffel N` and the like is generic (`GENERIC_RE`). The show guess reads a dotted `Season.2` as a marker, and a channel layout glued to its codec (`DD5.1x264`, `vfs::is_channel_layout_codec_at`) as no `NxM` marker. The marker check and the choice of the largest file read only the selected files (`served_files`; every file counts while none is selected, e.g. a Real-Debrid torrent waiting for its file selection), because Real-Debrid lists unselected files too and the VFS never shows one, so a partly selected collection is named after the film it serves. A cached `matches` entry keeps the identification it was made with. The guess helps pick between TMDB's TV and movie results when neither is an exact title-and-year match, and it is the media type of an unidentified torrent (`fallback_metadata`). A TMDB search returns a `SearchOutcome` that distinguishes a genuine empty result (a real "no such title") from a **failed** request (`Unavailable` — a transport error, a 429 or 5xx after the retry budget, another 4xx, or an undecodable body). During a TMDB outage `identify_name` short-circuits its multi-stage fallback ladder (CamelCase split / prefix strip / after-dash / no-year retry) on the first `Unavailable` rather than re-issuing a full ~2.5-min retry cycle per stage (which would burn ~10 min of doomed retries on one unidentifiable torrent); a genuine empty result still drives the whole ladder. `identify_name` returns `Identification::{Identified, NoMatch, Unavailable}`. `Unavailable` means a TMDB search failed (an outage past the client's retry budget, or a 4xx such as a rejected API key), whether or not something matched: with one half of the joined TV/movie search missing, or the ladder cut short, the best pick among the remaining results can be an unrelated title, so it is no verdict on the name (the scan loop doesn't cache it and the title check defers instead of rejecting). `identify_torrent` skips the torrent-name retry once TMDB is unreachable and returns the name-derived fallback (`external_id: None`); the scan loop detects that outage with `tmdb_client::track_search_failures`. A torrent left unidentified because a TMDB search FAILED (`tmdb_client::track_search_failures`) is not cached: the scan loop shows it under its fallback title and identifies it again after 15 minutes (`TMDB_RETRY_AFTER`); a genuine no-match is cached as before. Within one scan tick, the first file-less refresh or identification that TMDB leaves unidentified trips a circuit breaker (`resolve_metadata_unless_tmdb_down`, shared by `refresh_fileless_infos` and `identify_new_torrent`): the rest of the tick's refreshes and the batch skip TMDB (an authoritative identification still resolves). A skipped torrent of the batch is shown under its previous fallback (or `identification::fallback_metadata`, the title a TMDB no-match yields, so the folder isn't renamed when TMDB answers), a skipped refresh stays out of the VFS, and both are retried after 15 min, so an outage costs one TMDB retry budget per tick, not one per due retry. A due retry keeps its fallback in the VFS until its new result replaces it in place.
- **Synchronous instant repair (provider-neutral):** When a media file is read, `dav_fs.rs` resolves the locator via `provider.resolve_url` (cached, so free when healthy). On `AppError::Unavailable`, it calls `repair_manager.try_instant_repair(&FileLocator) -> Result<FileLocator, _>` synchronously — re-adds the torrent by hash, selects the same files, and checks if the replacement is already cached. Success is decided by the new torrent reaching `status == "downloaded"` **plus** a `file_path` match for the same file (there is no `InstantRepairResult` type, and no RD-specific link-count check — path matching is inherently safe, and the replacement file is located by matching `file_path` rather than the old positional index into RD's `links` array). On success it returns a fresh `FileLocator` for that file — pairing the per-file restricted `link` by position among selected files for RD, or leaving `link: None` for providers that resolve by `(torrent_id, file_id)` (TorBox). `dav_fs` installs the returned locator (invalidating the old resolution) and re-resolves inline, so playback continues after a brief delay. For a new-id (Real-Debrid) repair, before it deletes the old torrent, the repair also records a redirect: the old torrent id mapped to each selected file's locator in the replacement (`RepairManager::repaired_locators`). `DebridFileSystem::open` opens every media file through `RepairManager::redirect` (which follows chains of repairs), so until the next scan rebuilds the VFS, later opens of the same file or a sibling file don't resolve the deleted torrent and fail. `try_instant_repair` consults the same redirect first, so a handle opened before the repair (a second reader of the file, or a long-lived sibling stream) whose read then fails gets the recorded copy instead of a doomed repair of the deleted torrent. `prune_health_status` drops a redirect once the listing has neither the old torrent nor the copy its chain of redirects ends at, and that copy isn't a replacement still waiting for the scan loop, so a handle opened before the repair reaches the replacement for as long as it exists. The repair is bounded to 30 s (`INSTANT_REPAIR_TIMEOUT`). A repair cut short, by that timeout or by the read awaiting it being dropped, leaves the torrent `Healthy`/visible with its attempt budget reset and its cooldown restarted at that moment. A new-id (RD) torrent it had added but not yet adopted is deleted in the background (`repair::UnadoptedAddGuard`): `reacquire::materialise` records the added id as soon as the add returns, and the repair takes it back before it adopts the add, so a repair cut short after that point never removes both copies. The scan loop's same-hash dedup could not clean up such an un-adopted add, since it only collapses `downloaded` torrents and an un-selected RD torrent never downloads. Once it has adopted the add, the repair records the replacement and updates the health map before the superseded torrent is deleted: on the cached path the new id gets the carried attempt budget and a fresh cooldown, and on the not-cached path the old torrent is marked Broken. The delete then runs in a detached task (`RepairManager::delete_superseded`). Awaited inside the 30 s bound, a slow or 5xx-ing Real-Debrid delete (it runs the full background retry budget) could time out a repair that had already succeeded, losing the replacement record and the carried budget. The repair's three torrent lookups (the torrent under repair, the re-add, the final check) retry a 404 after 0.5 s and 1 s (`repair::REPAIR_INFO_NOT_FOUND_BACKOFF` via `provider::torrent_info_retrying_not_found`) for TorBox's spurious `mylist?id=` 404. If **not** cached on a genuinely-new id (RD), the file fails, the new torrent is left to download, the old torrent is marked Broken, and the replacement is recorded (scan loop picks it up). **Same-id re-add (TorBox):** TorBox's `createtorrent` recovers the existing torrent by infohash, so a repaired-in-place torrent keeps its **same** id (`new == old`); the repair therefore never deletes it (deleting would destroy the very torrent it repaired — and for mirror/manual content that would be permanent loss), records no replacement, and passes `protect_id` to `reacquire::materialise` so a transient post-add failure can't delete the real torrent either. **Visible on no-replacement failures:** a repair that produces no usable replacement (a transient re-add/info error, or a same-id torrent that's merely re-downloading) leaves the torrent **`Healthy`/visible**, NOT `Broken` — because `read_bytes` short-circuits on `should_hide_torrent` *before* any I/O, a hidden torrent can never re-trigger repair, so marking it Broken with no replacement would trap it until restart. `Broken` is set ONLY where a replacement IS recorded (the not-cached new-id path). **Cooldown + attempt cap survive re-adds:** the repaired torrent's health carries the old entry's `repair_attempts` plus a fresh cooldown trigger to the new id (RD mints a new id each repair), so the 30s cooldown + max-3-attempt cap hold *across* re-adds — bounding a still-broken-on-CDN cached file to ≤3 re-adds rather than a per-read storm. `prune_health_status` runs against the listing fetched at the start of the scan tick. It keeps the new id's entry while its replacement is still waiting in `repair_replacements` (which `complete_repair` records before inserting that entry), so a repair that completes mid-tick keeps its carried budget. A confirmed good byte read (`note_read_success`, called once per opened file) **resets** the budget, so the cap counts only *consecutive* failed repairs (a storm), not unrelated incidents over the deployment's lifetime (which would otherwise accumulate to a permanent `Failed`).
- **Repair hides broken torrents (provider-dependent):** On the not-cached repair path with a genuinely-NEW id (Real-Debrid), the old torrent is marked Broken and hidden from WebDAV until the scan loop picks up the recorded replacement. On a SAME-id re-add (TorBox's `createtorrent` recovers the existing torrent by infohash), and on any repair failure that records NO replacement, the torrent is instead kept `Healthy`/visible — because a `Broken`/hidden torrent can never re-trigger repair (reads short-circuit on `should_hide_torrent`), so hiding it with no replacement would trap it until restart (see the instant-repair design decision above). A torrent mid-repair (`Repairing`) is NOT hidden from the VFS (`hidden_torrent_ids`, the VFS and repoint filter, holds only `Broken`/`Failed`), so a scan tick that lands inside a repair doesn't drop its files or tell Jellyfin they were deleted; `should_hide_torrent` still refuses its reads until the repair settles.
- **SP1 Acquisition Engine (historical — superseded by the SP3 optimistic-add model below; `acquire` no longer materialises/validates/probes synchronously, it adds the best candidate and defers the verdict to `observe`):** When a title is requested (by the SP2 Trakt reconciler — `reconcile_wanted`/`monitor_episodes` — which replaced the temporary `--acquire` CLI), the engine originally ran: (1) **Scrape** — `TorrentioScraper` calls a Stremio-compatible addon (default: Torrentio, URL auto-templated from `<provider>=<token>`; override with `SCRAPER_ADDON_URL`). (2) **Score/rank** — `release::parse` extracts resolution, codec, HDR, size, seeders, cached flag, and source tier; `release::rank` hard-filters the resolution ceiling (`MAX_RESOLUTION`), cam/telesync/screener sources, **and uncached zero-seeder (undownloadable) releases** (so the engine never burns acquire attempts on dead torrents or leaves "checking" magnets behind), then sorts by a weighted score: cached availability dominates, then **resolution within the `MAX_RESOLUTION` ceiling** (a user who raises the ceiling to 2160p wants 4K, so resolution outweighs source tier), then source tier [REMUX>BluRay>WEB>HDTV], then progressively smaller **additive** bonuses — HEVC (+5k), HDR (+3k), verifiable container (+2k), bitrate (up to +3k), seeders (up to +2k) — which **combine into the weighted sum rather than forming a strict tie-break chain** (e.g. the HEVC bonus can outweigh a one-step source-tier difference, and bitrate can outweigh the container bonus; `rank` orders by cached, resolution and the language penalty first, then tagged source before untagged, then that sum, so the HEVC bonus never lifts a release with no source tag above a tagged one at the same resolution), with a configured-`AUDIO_LANGUAGE` mismatch applied as a large penalty; see `release::score` for exact magnitudes. (The default `AUDIO_LANGUAGE=original` is resolved per-title via `QualityPrefs::with_resolved_audio(original_language, spoken_languages)` **before** ranking — to `Lang(x)` when the title's TMDB original ∪ spoken languages (`config::original_audio_languages`: de-duplicated, original first) is one language, `AudioReq::AnyOf(..)` when several (never produced by parsing the env var), unchanged `Original` when none is known — exactly how `probe::verify` resolves `Original` — so a wrong-language release is down-ranked up front rather than ranking #1, getting optimistically added, and only then being rejected at probe time; a release in a spoken language (e.g. a `fi`-original film whose dialogue is mostly English) is not penalised. Accepted trade-off: a dub in a secondary spoken language is accepted too.) (3) **Materialise** — re-adds the torrent by hash, waits for the file list, and selects the target file; **a movie request whose materialised torrent has more than one feature-sized video is rejected as a multi-movie pack** (providers like TorBox auto-select all files). (Post-SP3 only `repair.rs` calls `reacquire::materialise`; `acquire`/`observe` add optimistically.) A candidate whose materialise *fails* (provider "already queued", or an add whose file list never resolves) has any leaked torrent for its hash deleted before the next candidate is tried, so a rejected/failed candidate never lingers as a dead "checking" torrent. (4) **STRICT title validation** — `TmdbTitleValidator` runs `identify_name` on the selected file's name and verifies the result resolves to the requested TMDB id; mismatches are blacklisted and the next candidate is tried. (5) **File-probe** — `HttpProber` fetches the first 4 MB of the CDN URL and uses the hand-rolled `probe::probe_tracks` (MKV/MP4) to extract audio/subtitle language codes; corrupt probes are blacklisted, wrong-language probes are blacklisted, unknown formats are accepted. (6) **Outcome** — `Acquired` (cached + verified), `Pending` (downloading or probe deferred), `NoAcceptableRelease`, or `TemporarilyUnavailable`. `observe` monitors Pending torrents each scan tick: stall detection (no progress for `STALL_TIMEOUT_SECS`), deferred probe retry (up to `MAX_VERIFY_ATTEMPTS`), and fail-and-reacquire. The `authoritative_ids` table overrides filename identification for engine-owned torrents; the `blacklist` table prevents re-adding rejected hashes.
- **Trakt-driven desired state (SP2):** A persisted `wanted` set (per user, per **(media_type, tmdb_id)** — so a movie and a show that share a numeric TMDB id are tracked independently; which sources want it — watchlist / in-progress — plus watched-state and, for shows, TMDB status, **and the IMDB id Trakt supplied**) is materialised from each enrolled user's Trakt account by `sync_trakt`, from reads that follow **every page** (Trakt paginates the watchlist + watched endpoints by default since 2026; a failed page fails the read — see the `trakt_client.rs` row) with watched shows requested as `extended=progress` (the only form that still carries per-episode watched state). **Catch-up source:** a show you've *watched* (from `/sync/watched/shows`) is also folded into the wanted-set as an in-progress source (so its unwatched aired episodes are auto-acquired, every one of them, including episodes that aired before the last watch), gated by `TRAKT_CATCHUP_LOOKBACK` (last-watched within the window; default all-time) and skipped when the show is already watchlisted or in progress (those sources already want it, and the watchlist its whole run): no `show_progress` call is made for it, and it is never a finish-cleanup candidate on this path. The catch-up membership is **precisely gated on Trakt per-show progress** (`GET /shows/{trakt_id}/progress/watched`): a within-lookback watched show is folded in **only if Trakt reports it has ≥1 unwatched aired episode** (`next_episode` non-null = behind), so fully-caught-up shows don't bloat the wanted-set or drive a fruitless reconcile each cycle. The progress check runs in `sync_trakt_user` (one call per catch-up candidate; on a missing Trakt id / progress error it conservatively includes the show — degrades to lookback-only rather than dropping a possibly-behind title) and is passed to the PURE `build_wanted` as the fold set. **Finish-cleanup fold:** a caught-up (not-behind) watched show that is **owned AND `Ended`** is a finish-removal candidate; `sync_trakt_user` LOGS these every sync (a preview) and — **only when `REMOVE_FINISHED_SHOWS` is set** — also folds them into the wanted-set so the episode monitor's (`monitor_episodes`) Trigger-A finish removal fires on its next run (every `TRAKT_EPISODE_CHECK_INTERVAL_SECS`, idle-gated) (removal + zero acquisition hold **when TMDB and Trakt agree on the aired set**; on a TMDB/Trakt aired-set disagreement the TMDB-authoritative reconcile keeps the show and catch-up acquires the genuinely-unwatched-per-TMDB episode instead — consistent, not a phantom acquire; in the opposite direction, when Trakt counts an aired episode TMDB lacks, Trakt reports the show behind, so it is in `behind`, marked `trakt_behind` and kept). When the flag is off they're preview-only and never folded, so nothing is removed. `finished_ended_candidates`/`shows_to_fold` are the pure helpers. A catch-up show acquires only the **unwatched** aired episodes (you want what you haven't seen); a **watchlisted** show acquires **every** aired episode (the whole run, even already-watched, for a re-watch); and `reconcile_title`'s Show branch won't acquire a show all watchers have *finished* (symmetry with Trigger A — a watchlisted show is never "finished", so it still acquires). **IMDB resolution prefers Trakt's id** (`WantedRecord.imdb_id`, carried through to the `Acquire` op) over re-deriving it from TMDB's `external_ids`, because TMDB's mapping is incomplete for some titles (e.g. a TVDB-only show) — `build_acquire_request` falls back to TMDB only when Trakt gave none, and returns `Ok(None)` (skip quietly, logged at debug — Torrentio is IMDB-keyed so it can't be scraped) when no IMDB id exists anywhere, rather than WARN-ing every reconcile tick. A PURE reconcile-core (`wanted.rs`) diffs wanted-vs-owned-and-available and emits acquire/remove `Action`s, executed by `reconcile_wanted` (movies incl. their Trigger-A/B removal + show Trigger-B removal) and `monitor_episodes` (show episode acquisition + Trigger-A finish removal, via TMDB air dates). There is **one shared household library**: acquisition is the union across users; removal is per-user-aware.
- **Removal lifecycle:** The Trakt lifecycle (Trigger A/B) removes only engine-acquired hashes (`removal_hashes` → `OwnedGroup.engine_hashes`), except a show finish-removed under `REMOVE_FINISHED_SHOWS`. Account-mirror copies (torrents the user added; empty provenance) are otherwise kept by the lifecycle, but can still be removed by dedup, by the upgrade prune when a better copy supersedes them, by `REMOVE_FINISHED_SHOWS` finish-cleanup, and by `observe`'s dead-status reap (`fail_and_reacquire`: a Real-Debrid `magnet_error`/`dead`/`error`/`virus` status on a record with an IMDB id; not idle-gated, since such a torrent can't be streamed). `Manual` provenance exists only on legacy records from the removed `--acquire` CLI; the Trakt lifecycle and dedup never remove it and the upgrade engine skips the whole title (M-1, `Provenance::has_manual_entry`), but a dead `Manual` torrent is still reaped by `observe` and re-acquired with its provenance kept. **Trigger A (finished):** every user who **in-progresses** the title has finished it (movie watched; show = 100% of *aired* episodes watched AND its TMDB status is `Ended` (ended or cancelled — `ShowStatus::Ended`; a returning/in-production/planned show never qualifies even if fully watched)). A show Trakt reports the user behind on (`WatchedState::Show.trakt_behind`, including one the sync assumed behind; see the `wanted.rs` row) is never finished, so Trigger A needs TMDB and Trakt to agree. Trigger A needs a current wanter. Trakt drops a finished title from `/sync/playback`, and a title still there never reads as finished (`tasks::build_wanted` writes a playback movie as not watched and a playback show as `trakt_behind`: the user is partway through it, a paused re-watch included; for a paused re-watch, meaning a pause on an episode the user had watched before pausing it (its `WatchedShow.episode_watched_at` is earlier than the pause's `paused_at`), it also drops the earliest such paused episode and every later one from that row's watched set, so a re-watch begun without a Trakt progress reset acquires from the pause on, a lapsed episode included, instead of none of it. A pause on an episode never watched (an abandoned first-watch pause) or watched only after the pause leaves the watched set alone, so a first watch acquires only its unwatched episodes, never the ones watched since), so in practice Trigger A fires only for a show folded back in by `REMOVE_FINISHED_SHOWS`; an in-progress-only movie whose wanted row is gone is kept (pinned by `wanted::tests::finished_in_progress_movie_no_longer_wanted_is_kept`). **A watchlisted title is NEVER finished-removed** — the watchlist is an explicit "keep this available" signal (re-watchlisting something you've watched means you want to re-watch it), so it stays acquired regardless of watched state and `trigger_a_finished` short-circuits to `false` while any user watchlists it. Without that guard a watched+watchlisted title oscillated acquire↔remove every reconcile tick (the acquire path ignores watched), flapping the library. **Trigger B (abandoned):** a watchlist-provenance user un-watchlisted it AND no user currently wants it (via either source) — this is the sole removal path for a watchlisted title. Otherwise the title is kept. Provenance is **sticky** — recorded at acquire time (one entry per wanting user+source) and preserved across re-acquire, including any `Manual` entry. Both removal triggers are executed through the **idle-gated** `execute_remove` (`UPGRADE_IDLE_SECS`), so a removal never tears content out from under an active stream (a non-idle library defers the removal to a later tick, leaving the owned record intact for retry).
- **Availability re-acquire:** A wanted title that is owned but no longer present in the provider listing is treated as lapsed (cache expired / lost) and proactively re-acquired. For shows this is per episode: an episode counts as covered only while a record that supplies it is present or still `Pending`, so an episode whose only copy left the account is re-acquired even while the rest of the show is present (`plan_episode_actions`).
- **Account mirror = owned (no protected "manual" class):** The scan loop's `record_mirror_owned` records every identified, present provider torrent the engine doesn't already track (except a hash the engine has blacklisted for ANY title, hash-wide via `all_blacklisted_hashes`, a hash with an open staging intent (an upgrade candidate or an acquisition being added, or cut off mid-add), and a torrent whose cached info lists no emittable video file (a lapsed TorBox entry, one listed with `files: null`, an archive-only torrent), which is adopted once its files are back; none of these is ever mirrored. An existing `Verified` mirror record is reaped as a phantom, store-only, with its authoritative id + selection slots, only when it is no newer than its hash's newest non-"Dead" blacklist entry: see the `tasks.rs` row) as a **`Verified` owned record with EMPTY provenance** (a show's `provides` = the SE-parsed set of its selected video files; a movie's is empty; `quality` is **derived from the representative/largest video file**, with any axis its name leaves untagged filled from the torrent name (`mirror_quality` → `QualitySummary::of_owned`) — `cached: true` since it is present — so the record is comparable on the dedup/upgrade/consolidation paths: an axis neither name tags is recorded as 0 (**unknown — the lowest quality** at its resolution, so a known cached release at or above that resolution that passes the probe may replace it), a file **above the resolution ceiling keeps its real resolution** (never unknown-lowest; replacing it is a gated corrective downgrade), and a torrent with no video file (a lapsed TorBox entry lists none) is not mirrored at all until its files are back. Older mirror records stored `None` for the first two cases; `backfill_owned_quality` re-derives their quality from their file names (scan loop + every upgrade tick): a still-`None` record, or a mirror record whose untagged resolution or source tier its file names now tag (`Store::replace_quality_if_eq`, a compare-and-set). An older record of a torrent that lists no video file (no quality, no `provides`) is dropped by the mirror pass instead. A recorded quality is flagged `unverified` iff the representative file isn't `.mkv`/`.mp4` (a mirrored MKV/MP4 was never probed either but is assumed fine — flagging it would churn the whole library) — set when the mirror record (or a backfilled quality) is created, so it covers mirror copies recorded from schema v8 on; a pre-existing mirror copy that already had a quality is **not** flagged retroactively (it has no `selection` entry for the v8 migration to find, and `record_mirror_owned` only fills a missing quality or heals an axis it left untagged, never otherwise rewrites one); `imdb_id` resolved from TMDB `external_ids`, cached per-title, best-effort; an id lost to a transient failure is filled by the daily `backfill_missing_imdb_ids`). This makes the reconciler/episode-monitor aware of the user's **pre-existing library**, so a watchlisted/in-progress title that is already present is **not re-acquired as a duplicate**, and a pre-existing season pack reports its episodes as owned (no per-episode `monitor_episodes` churn). Empty provenance means the record is owned **exactly like an engine-acquired title** — eligible for the daily quality-upgrade / consolidation path (the replacement of an upgraded mirror copy stays a mirror record: empty provenance; deliberately NOT a `Manual` protected class, so manually-added content follows the same upgrade path) — while still being **kept** under the normal lifecycle: with no Trakt wanter and no watchlist provenance, neither removal trigger (`trigger_a_finished`/`trigger_b_abandoned`) fires for a mirror-only group, and Trigger **B** (abandoned watchlist) never deletes a mirror hash even when it shares a `tmdb_id` with watchlist-acquired episodes (removal is scoped to the group's engine-acquired hashes — `OwnedGroup.engine_hashes` — via `removal_hashes`). It is idempotent and non-destructive — an engine-owned or already-mirrored hash is never clobbered. It trusts the identification: a torrent matched to the wrong title is mirrored under that title's TMDB and IMDB ids, so the upgrade engine replaces and prunes it as that title (`supersede_hashes` never looks at what a copy holds) and dedup groups it with real copies, and nothing re-identifies a cached match. README warns operators to check a new deployment's library with `UPGRADE_INTERVAL_SECS=0` first. A real guard needs a stored identification confidence or a per-title override; re-running `validate_title` on the owned file name would only repeat the wrong match. `observe`'s dead-torrent re-acquire skips only records with **no IMDB id** (can't re-scrape → leave for on-read repair), not by provenance. **A mirror hash (empty provenance) is protected from the general Trakt removal lifecycle**, even when a Trakt user *wants* the title (it shares the `tmdb_id`): a removal must never delete content the engine didn't acquire (the sync no longer writes a title still in `/sync/playback` as finished, so for a paused re-watch this guard is a backstop). `removal_hashes` enforces this — for a `Finished` (Trigger A) removal it returns only the group's **engine-acquired** hashes (`OwnedGroup.engine_hashes`) EXCEPT in the one opt-in case: a **show** with `REMOVE_FINISHED_SHOWS=true`, where the finish-cleanup *folds* fully-watched ended owned shows into the wanted-set specifically to reclaim the full set (incl. pre-existing library copies). Trigger **B** (abandoned watchlist) also returns only engine hashes. So a mirror torrent is removed only by (a) the explicit duplicate-dedup pass (where it gets **no** protection — it competes on quality like any engine copy) or the upgrade engine superseding it with a better release, (b) `REMOVE_FINISHED_SHOWS=true` show finish-cleanup, (c) when it is *also* engine-acquired (mixed group) and that engine hash is reclaimed, or (d) `observe`'s dead-status reap (`fail_and_reacquire`, Real-Debrid statuses only, not idle-gated since the torrent can't be streamed; a movie is replaced, a mirror show record is not). A pure-mirror **movie** is never finish-removed (movies are never folded). `reconcile_title`'s symmetric acquire-side guard (both the Movie and Show branches short-circuit on `trigger_a_finished`, except for manual content) means an engine-reclaimed title is **not** re-acquired the next tick — no acquire↔remove flip-flop; to keep a watched title available, watchlist it.
- **Multi-user enrolment:** Accounts are linked via device-flow OAuth on the local-network enrolment page (`/trakt/accounts`, served on the WebDAV listener — no auth, trusted-LAN model; the routes answer only for local-network `Host` names, plus `TRAKT_ENROL_ALLOWED_HOSTS`, reject cross-origin POSTs, and refuse to be framed (`frame-ancestors 'none'`, `X-Frame-Options: DENY`)). Tokens are refreshed once they expire within `REFRESH_BUFFER_SECS` (1 h): Trakt access tokens last 24 h, and a longer buffer would refresh, and rotate the single-use refresh token, on every sync. Tokens are keyed by Trakt **slug**. A token-refresh or read failure — including a failure of **any page** of a paginated read, or a list seen to change mid-read (the `trakt_client.rs` row names the one shift that isn't seen) — marks the account `needs_reenrolment` (shown on the page as "⚠ the last sync failed" with what to do; cleared by the next successful sync) and leaves its prior `wanted` set intact — the reconciler never acts on a failed or truncated fetch. A transient refresh failure (a persistent 429, a 5xx, a transport failure or an incoherent answer: `trakt_client::refresh_error_is_transient`) skips the cycle without flagging `needs_reenrolment`, both in background sync and for the page's Refresh button; a 4xx such as `invalid_grant` still flags. Remove is two-step: a GET confirmation page that warns what the next sync will delete (all watchlist-acquired content when it is the last account), then the POST that removes.
- **`--acquire` CLI removed:** The temporary SP1 verification CLI was deleted in SP2; Trakt sync + the reconciler are the acquisition triggers now. A `scheduler.rs` source-guard test (`acquire_cli_is_removed`) fails if the flag is reintroduced into `main.rs`.
- **Database is self-healing (but only for genuine corruption):** `Store::open` stamps a schema version and runs forward migrations. A genuinely corrupt / damaged `metadata.db` (a bad-header `Io(InvalidData)`, a truncated file, redb's `Corrupted`/`RepairAborted`) is **moved aside** to `<db_path>.corrupt` (or `<db_path>.corrupt.<n>` when that name already exists, so an earlier backup is never clobbered) and recreated rather than crashing the service. The old file is kept as `<db_path>.corrupt`, but the recreated DB starts without the Trakt enrolments, provenance, selections and blacklist (only the `matches` cache and the `upgrade_checks` cursor regenerate), so this is not lossless. A truncated file whose intact header records a longer layout makes redb panic inside `Database::create`; `try_open` catches the panic and treats it as corruption. Authoritative tables added in later phases are migrated, never silently dropped (e.g. v7→v8 rewrites owned records in place to flag `quality.unverified` on those a `selection` entry serves from a non-MKV/MP4 file — engine-acquired copies; pre-existing account-mirror copies have no selection entry and are not flagged retroactively). A **transient/incompatible** open failure — another instance holding the lock (`DatabaseAlreadyOpen`), a permission/disk I/O error, an intact database in an older `redb` on-disk format (`UpgradeRequired`, e.g. after a `redb` dependency bump), an intact database in a NEWER `redb` on-disk format (redb reports it as `Corrupted("Expected file format version <= N, found M")`, which `db_open_failure` classifies as transient), **or a schema written by a NEWER build of this app** (our stored schema version is ahead of the binary, e.g. after a rollback) — is classified separately (`db_open_failure` / the `try_open` version check) and **fails startup** instead of discarding a possibly-intact database (its authoritative `owned_hashes`/`authoritative_ids`/`selection`/`trakt_tokens` tables are not regenerable, and `wanted` only comes back once the accounts are re-enrolled, so the operator rolls the binary forward / backs up / migrates rather than losing them). The newer-schema case is treated like `UpgradeRequired` — intact-but-unusable, never moved aside. The test-only constructor `Store::from_database` (`#[cfg(test)]`, behind `Store::in_memory` and the `fail_writes` helpers) refuses it too.
- **SP3 — Optimistic-add + asynchronous reconcile (always-on robustness + daily quality):** `acquire` now **adds the best candidate optimistically** and records it `Pending` — no synchronous 15s poll, pack-guard, title-validation, or probe. `observe` (every scan tick, no scraping) is the resolver: once files appear, the deferred gates run; on pass it marks `Verified`, records `provides` (which `(season, episode)` pairs the hash supplies) and a `quality` summary, and writes `selection` entries; on fail it blacklists the hash and re-scrapes for the next-best candidate. Genuinely-dead torrents (provider error status, or no resolution after `ACQUIRE_DEAD_TIMEOUT_SECS`) are reaped and re-scraped. **Selection inversion:** "which release represents this title/episode" is a persisted `selection` table (slot → `{hash, file_path}`) that `vfs::build` consults on every scan; a slot with no managed selection keeps the pre-SP3 behaviour (a movie's largest streamable torrent; every distinct file name of an unmanaged show episode, which under canonical episode names is one file per episode). **`provides` kills season-pack churn:** the union of `provides` across a show's owned hashes is the owned-episode set — a season pack reports all its episodes as owned so `monitor_episodes` never re-acquires them. **Daily upgrade engine** (`upgrade.rs`, on by default, disable with `UPGRADE_INTERVAL_SECS=0`): re-scores every eligible owned title each pass (see the `upgrade.rs` row; copies of unknown or unchecked quality first; `UPGRADE_BUDGET_PER_TICK` caps it) and stages a meaningfully-better CACHED release (`is_target_improvement`: uncached→cached, or a strict `score` gain on a category jump — a higher resolution, or a higher source tier at the same resolution: never trading resolution for tier, nor tier for a bonus — that still holds with the candidate scored under the title's resolved audio as acquisition ranks it, so a wrong-language-tagged release acquisition would rank below the owned copy is never adopted — or, for an owned copy flagged `unverified` (its tracks couldn't be checked), any equal-or-better cached release at the same-or-higher resolution — or, for an owned copy of **unknown quality** (none recorded, or an untagged resolution/source tier: the lowest quality), any known-quality cached within-ceiling release at or above its tagged resolution; an unknown candidate never improves a cached copy within the ceiling (an untagged-source one may still correct an over-ceiling copy), and an over-ceiling copy is never unknown); staging adopts only a probe `Pass`, so an upgrade never swaps a checked copy for an unchecked one; idle-gated swap (`UPGRADE_IDLE_SECS`) + prune of the superseded torrent ensure an active stream is never interrupted. The staged replacement inherits the provenance of the copies it supersedes (`upgrade::superseded_provenance`), and gets an empty one as soon as one of them is a mirror record, so an upgraded mirror copy stays a mirror record. **Shows now get the same quality-upgrade treatment as movies, at per-episode granularity:** every owned singleton episode is independently re-scored and swapped, run BEFORE that season's pack/consolidation handling so a freshly-upgraded episode can still be folded into a pack later the same tick. **Episodes served from a within-ceiling multi-episode pack** are then re-scored against the pack's quality and moved to a better cached true singleton at the same-or-better source tier and resolution (consolidation's no-regression test; since no upgrade lowers a single's tier at the same resolution, consolidation never folds the split pack back — bar one re-fold of an unverified pack split into equal-quality singles) the same way; the pack is pruned only once it serves no slot and every episode it provides is held by another `Verified` owned record that is still present on the provider (otherwise kept), with a sample-first bound (a first served episode with no improving candidate, or whose only improving candidates turn out to be season packs, skips the rest of that pack this visit). **Corrective downgrade (opt-in):** when `MAX_RESOLUTION` is lowered below an already-owned copy's resolution, `effective_score` penalises that copy so a within-ceiling CACHED candidate now reads as an improvement (`Improvement::Downgrade`); this only executes swap+prune when `ALLOW_RESOLUTION_DOWNGRADE=true`, applies to both a movie/episode singleton AND an over-ceiling season pack (`correct_over_ceiling_packs`, same same-episode-coverage + idle-gated-swap discipline as consolidation), and is a no-op — logged as a preview (`upgrade: … would downgrade …`) — when unset (the default) or when no conforming cached replacement exists (a sole over-ceiling copy is kept, never deleted with nothing to replace it). **Full-season consolidation (unchanged, layered after the per-episode passes):** the same engine finds a CACHED full-season pack covering all aired episodes at same-or-better quality and consolidates scattered per-episode torrents into it, idle-gated; consolidation itself never regresses quality and is not part of the downgrade path. No show swap deletes a copy holding a video file with no episode code that its record doesn't account for (an OVA, an anime absolute number in a mirrored pack), since `provides` leaves that file out and no other copy holds it: the slot moves and the old copy stays.

## Development Process

- **Test-Driven Development (TDD) is required.** When implementing new features or fixing bugs:
  1. Write a failing test first that captures the expected behavior.
  2. Write the minimum code to make the test pass.
  3. Refactor while keeping tests green.
  4. Run `cargo test` after every change to confirm nothing is broken.
- **Before every commit, run the lint gate (fmt + clippy, as in CI's `lint` job; that job also checks THIRD-PARTY-NOTICES, see below):**
  ```bash
  cargo fmt --check && cargo clippy --all-targets --locked -- -D warnings
  ```
  CI runs these on the latest stable Rust (`dtolnay/rust-toolchain@stable`), and each new stable
  can add clippy lints — so keep your local toolchain current (`rustup update stable`), otherwise
  lint can pass locally yet fail in CI on a lint your older clippy doesn't have. Cargo.toml's `rust-version` (1.96) matches the Dockerfile builder (`rust:1.96-slim`), so clippy's `incompatible_msrv` lint fails the lint job on a std API newer than the image's compiler. CI's `msrv` job runs `cargo check --locked --all-targets` on that same toolchain (`dtolnay/rust-toolchain@1.96`), so a dependency or language feature newer than the builder fails the pull request, before it can break the post-merge Docker build. Cargo.toml also sets `resolver = "3"`, so `cargo update` and Dependabot prefer dependency versions compatible with `rust-version`. Bump the three together: `rust-version`, the Dockerfile `FROM` line and the `msrv` job's toolchain. If
  `cargo fmt --check` fails, run `cargo fmt` to fix; do not hand-format around it. When the commit
  touches Cargo.lock, also run the lint job's notices check (it writes to a scratch directory, never
  the repo):
  ```bash
  cargo about generate --offline --locked -o "${TMPDIR:-/tmp}/THIRD-PARTY-NOTICES" about.hbs \
    && diff -u THIRD-PARTY-NOTICES "${TMPDIR:-/tmp}/THIRD-PARTY-NOTICES"
  ```
- **Advisory audit:** `.github/workflows/audit.yml` runs `cargo audit --deny warnings` (RustSec vulnerabilities, yanked and unmaintained crates) on every push and pull request to main and v2, and weekly (Mondays 06:00 UTC). The weekly run uses main's copy of the file, so it audits both lines' lockfiles only once the file is on main. It is a separate workflow, so an advisory never blocks lint, test or publish. Dependabot alerts cover only main's Cargo.lock, and dependabot.yml takes effect only from main. Run `cargo audit --deny warnings` locally after a dependency change.
- **Before every commit, run all unit and integration tests.** The core gate runs for every configured provider:
  ```bash
  # Blank the token of a provider whose account is inactive first, e.g. `export RD_API_TOKEN=`
  # (a blank exported value beats .env). A set token the provider rejects fails the gate.
  # --show-output prints a passing test's stderr, so a cleanup WARNING (see below) is visible.
  cargo test --locked \
    && cargo test --test lifecycle_test -- --ignored --show-output \
    && cargo test --test probe_integration_test -- --ignored --show-output \
    && cargo test --test repair_integration_test -- --ignored --show-output \
    && INTEGRATION_TEST_LIMIT=10 cargo test --test integration_test -- --ignored
  ```
  Integration test binaries must run sequentially (not `-- --ignored` on all at once) because they share the live provider accounts and their rate limits, and the ignored set also holds the interactive Trakt test and full-library scans. The live provider tests skip a provider whose token is unset or blank, so configure only the providers you hold a live account for and blank a lapsed token (dotenvy doesn't override an exported value). `repair_integration_test` repairs live on both providers. The `protect_id` path (a transient failure after a same-id re-add) is covered only by `MockProvider` unit tests in `repair.rs`. Do not commit if any test fails. (CI and the Docker build run with `--locked` — if you bump `Cargo.toml`, run `cargo test --locked` / `cargo build --locked` locally too so a stale `Cargo.lock` is caught before CI rather than silently updated.)
  - `lifecycle_test` is the cross-provider add→appears→delete→disappears check, plus per-provider `lifecycle_acquire_sintel_by_imdb_real_debrid` / `lifecycle_acquire_sintel_by_imdb_torbox` tests (sharing `run_acquire`) that exercise the SP1 `AcquisitionEngine` end-to-end against each live provider. With both tokens set, both providers' acquire tests run; they don't go through `choose_provider`, which refuses that combination. It runs against **both** Real-Debrid and TorBox, **modifying the live account** (adds and deletes a Creative-Commons *Sintel* torrent, cleaning up after itself). Each provider's sub-test **skips** if its token (`RD_API_TOKEN` / `TORBOX_API_KEY`) is unset or blank, so it is safe to run with only one provider configured. The binary's tests hold a shared mutex (`LIVE_ACCOUNT`), so the default parallel harness never has two of them adding and deleting Sintel in one account, and they clean up through `common::with_cleanup`, which also runs when an assertion fails. A cleanup first deletes the torrent ids the body recorded (`common::AddedIds`: `add_magnet`'s id, or for `run_acquire` the ids of listed torrents its store owns), then sweeps by hash with up to 3 listings 2 s apart (`common::delete_ids_then_sweep`), so a lagging TorBox listing doesn't leave a Sintel copy behind. It never deletes a torrent twice: an id the body deleted itself (the lifecycle delete step, a release `observe` rejected, the original a Real-Debrid repair replaced) is dropped from `AddedIds` (`common::forget_added_id`), and a torrent the cleanup deleted that a lagging listing still shows is only listed again, since TorBox answers a delete of an id already deleted with `500 DATABASE_ERROR`, which its client retries five times. It prints `WARNING: live-test cleanup may have left a torrent behind: …` on stderr naming any hash or id it couldn't confirm gone (one it deleted is marked "deleted but still listed"). `probe_integration_test` and `repair_integration_test` use the same `cleanup_added`. Before it adds anything, each `lifecycle_test` test runs `common::preclean_sintel_candidates`. It scrapes Sintel (`common::SINTEL_IMDB`, tt1727587) with the provider's Torrentio scraper (or `SCRAPER_ADDON_URL`), lists the account, and deletes every torrent with `SINTEL_HASH` and every scraped Sintel release whose name mentions Sintel, naming each in a WARNING on stderr. A scraped release whose name does not mention Sintel is only named, never deleted. Without this, a Sintel release a killed acquire run left stayed in the shared account for good: the next run's fresh store does not own it, so its acquire skips it and adds another release. A failed scrape still deletes `SINTEL_HASH`, and a failed listing still sweeps it. The live gate adds and deletes Sintel in whatever account the token names, and a deployment sharing that account mirrors the copy (and notifies Jellyfin) while the tests run. If a cleanup WARNING appears, delete the named torrent by hand; that deployment's mirror reaper then drops its record on its next daily prune. Better still, run the gate against a separate test account. libtest captures a passing test's stderr, so these WARNINGs show only with `--show-output` (which the gate passes) or `--nocapture`. Each `lifecycle_acquire_sintel_by_imdb_*` test builds its VFS from the acquired torrent alone and asserts that torrent is under `Movies/`; with a provider token set, a missing `TMDB_API_KEY` or a TMDB failure fails it. Right after an add, TorBox's backend can be briefly inconsistent: the listing may leave out a torrent whose own lookup already reports `downloaded` (the same lag behind its spurious `mylist?id=` 404s). So the "appears in get_torrents()" step polls the listing every 2 s for up to 30 s (`common::poll_until_listed`), and its failure message says whether the listings errored or left the torrent out; `find_ids_by_hash` returns the listing error instead of reading it as no torrent.
  - `repair_integration_test` runs against every configured provider (each provider's tests skip when its token is unset or blank) and **modifies the live account**. `test_instant_repair_of_sintel_real_debrid` / `_torbox` add the Creative-Commons *Sintel* torrent, wait until the listing shows it (`common::poll_until_listed`, since TorBox's listing lags an add and its re-add recovers an existing hash through the listing), mark it broken, instant-repair it and delete every Sintel copy afterwards, also when the test fails. On Real-Debrid the repair re-adds the hash under a new id, and the test checks that the original is deleted. On TorBox the re-add returns the existing torrent, and the test checks that the repaired torrent kept its id and still exists (its lookup retries TorBox's spurious `mylist?id=` 404). Neither test ever repairs one of the account's own torrents. `test_broken_torrents_hidden_from_webdav_real_debrid` / `_torbox` only read the account, through `common::ReadOnlyProvider`.
  - `integration_test` runs against every configured provider (Real-Debrid with `RD_API_TOKEN`, TorBox with `TORBOX_API_KEY`; a blank token counts as unset), skips when neither is set, and needs `TMDB_API_KEY`. It only reads the account: every call goes through `common::ReadOnlyProvider`. `INTEGRATION_TEST_LIMIT=N` caps the torrents identified in each account. Each provider's identifications are cached through `Store` at `$CARGO_TARGET_TMPDIR/integration_test_cache_<provider>.redb` (`real-debrid` or `torbox`, since torrent ids are per provider), never in the service's `metadata.db`. A failed TMDB search (`tmdb_client::track_search_failures`) fails the run and is never cached, as in the scan loop, and a torrent cached as unidentified is identified again on every run, so a fallback cached during an outage heals. An identified torrent whose cached file list holds no streamable video file (a TorBox torrent cached while it listed `files: null`, or while its cache had lapsed) has its files looked up again on each run. A fresh list that holds one replaces the cached list, and the identification is kept. A lookup that fails or still lists none keeps the cached entry, so the completeness check never covers such a torrent with no files for good. A torrent lookup that answers 404 is retried after 1, 2 and 4 s (TorBox's spurious `mylist?id=` 404s). Its `test_vfs_completeness` checks the VFS against what the build is meant to show with no managed selection: one copy per movie, and each distinct episode file name once per season folder of a show (the build it checks serves original names). `test_vfs_canonical_names` builds the same library with canonical episode names and fails when an episode the original names show (by its first `SxxEyy` code) has no file in that season folder, or a canonical name's code names another season; the offline `canonical_names_lose_no_episode_of_the_sample_library` runs the same check. A copy counts as hidden only when the season folder it belongs in already shows a file of that name, so a build that drops `Season 02/01.mkv` is not excused by `Season 01/01.mkv`. The test restates the build's season rule in `season_folder`, and the offline `season_folder_agrees_with_the_build` pins it to the build's placement. Other copies count as hidden by design, and selected video files without a positional link (selected-file/link-count mismatch) are counted separately and tolerated up to 20%; a torrent with no links at all (TorBox, which resolves by id) counts as streamable. Any other missing file fails it. `check_completeness`, the cache rules and the 404 retry are unit-tested offline in the same file, against a fictional `FakeAccount`.
  - `probe_integration_test` probes a cached *Sintel* file through BOTH providers' CDNs and asserts the probe reaches a verdict without deferring, guarding the 206/200 range-response handling. It runs RD + TorBox, each skips if its token is unset or blank, and it cleans up after itself.
- **Integration tests must be updated for new functionality.** When adding or changing features, update the integration tests to cover the new behavior. Integration tests are the final gate before committing.
- **Additional integration test files** (all `#[ignore]`, require API tokens): `test_all_rd_torrents.rs`, `test_short_titles.rs`, `test_media_generation.rs`, `video_player_simulation.rs`, `trakt_smoke_test.rs`, `sp1_live_test.rs` (live Torrentio scraper smoke, incl. `scraper_live_through_http_proxy` which validates `SCRAPER_PROXY_URL` against a real proxy — negative control + positive case, the latter skipped when the proxy isn't routable). These are supplementary and not part of the pre-commit gate. `cargo test --lib -- --ignored` runs the 10 live-TMDB identification regression tests in `src/identification.rs` (short-title disambiguation, collection-prefix stripping; the absolute-episode pack check is the offline `a_dash_coded_season_pack_is_identified_by_its_show_name`). They are read-only and need only `TMDB_API_KEY` (they panic without it rather than skip); run them when changing `identification.rs`. They load `.env` through `crate::config::load_dotenv()`, so a `.env` it can't load fails them. `test_all_rd_torrents.rs` and `test_media_generation.rs` skip when `RD_API_TOKEN` is unset or blank. `video_player_simulation.rs` only reads the account: every provider call goes through `common::ReadOnlyProvider`, which refuses `add_magnet`/`select_files`/`delete_torrent`, so the instant repair a failed read would trigger can't re-add (TorBox) or delete (Real-Debrid) a library torrent; such a read fails instead. Helpers shared by the live test binaries (`SINTEL_HASH`, `SINTEL_IMDB`, `ReadOnlyProvider`, `load_env`, `token`, `tmdb_client`, `find_ids_by_hash`, `INFO_NOT_FOUND_BACKOFF` (the 1/2/4 s 404 retry passed to `torrent_info_retrying_not_found`), the per-provider `label`/`token_var`/`client`/`provider_token`/`provider` (the token lookup with its skip line, and the client construction), `poll_until_listed`, `cleanup_by_hash`/`delete_by_hashes`/`cleanup_added`/`delete_ids_then_sweep` (with `AddedIds`/`record_added_id`/`forget_added_id`), `with_cleanup`, `preclean_sintel_candidates` (with the pure `sintel_leftovers`), `add_sintel_downloaded`, which takes an `&AddedIds` and records the new id right after the add, `encode_path_preserve_slashes`) live in `tests/common/mod.rs`. Every live test binary loads `.env` through `common::load_env` / `common::token` (enforced by `config::tests::live_tests_load_env_only_through_load_dotenv`, which also scans `src/*.rs` bar config.rs), so a `.env` line dotenvy can't parse fails the live tests instead of letting a test whose token sits below it skip and pass.
- **Worktrees:** don't share a `CARGO_TARGET_DIR` between git worktrees of this repo. The root package's artifacts get identical names, so one worktree's `cargo test` can run a test binary built from another worktree's sources.
- **Interactive Trakt live integration test** (`tests/trakt_integration_test.rs`): validates every Trakt parser and `sync_trakt` end-to-end against a real account without requiring a pre-existing token. Run with `cargo test --test trakt_integration_test -- --ignored --nocapture`; the test prints a URL + code, waits until you open it and approve on trakt.tv/activate, then exercises all reads, asserts that watched shows carry their per-episode watched data (the `extended=progress` regression guard) and that the `wanted` set is populated. It also asserts that every watched show with watched episodes carries their per-episode `last_watched_at` (`WatchedShow.episode_watched_at`), and warns when no in-progress show carries a paused regular episode (`paused_at`). The paused re-watch detection in `tasks::build_wanted` reads both. Requires `TRAKT_CLIENT_ID`, `TRAKT_CLIENT_SECRET`, and `TMDB_API_KEY`; skips cleanly if any is unset. The enrolled account's live tokens are kept in a per-run 0700 directory under Cargo's `CARGO_TARGET_TMPDIR` (not the shared system temp dir). The test prints its path and deletes it when the test ends, including on a panic; delete it yourself if you abort the run with Ctrl-C.
- **THIRD-PARTY-NOTICES is generated, never hand-edited.** cargo-about (`cargo install --locked cargo-about@0.9.3 --features cli`, the version CI pins; see below) builds it from `about.toml` (accepted licences in preference order, the release targets x86_64/aarch64-unknown-linux-musl, dev-dependencies excluded, the crate itself skipped via `publish = false`) and the plain-text template `about.hbs`. Regenerate it whenever Cargo.lock changes, including after a Dependabot cargo bump: `cargo about generate --offline --locked -o THIRD-PARTY-NOTICES about.hbs`. CI enforces it: the `lint` job in ci.yml and release.yml installs cargo-about 0.9.3 (`taiki-e/install-action`), regenerates the file into `$RUNNER_TEMP` and `diff -u`s it against the committed one, so a Dependabot cargo PR fails until the regenerated file is pushed and a release with stale notices stops. Regenerate with the same cargo-about version as the CI pin; when you upgrade cargo-about, bump the pin in both workflows and the install command above in the same commit. It reproduces upstream licence files byte for byte, so `git diff --check` reports trailing whitespace and CRLF lines in it; that is expected.
- **Before every commit, validate that `CLAUDE.md` and `README.md` are up-to-date.** If the commit introduces new features, env vars, modules, architectural changes, or modifies existing behavior, update both files to reflect the changes. Documentation must stay in sync with code at all times.
