# `torbox_client.rs`

TorBox implementation of `DebridProvider` (`mylist`/`requestdl`/`createtorrent`/`controltorrent`); resolves by `(torrent_id, file_id)`, ~3h URL cache; `mylist` re-lists the same way when one of our deletes may have shifted its pages (`provider::DeleteTracker`); each `mylist` page's offset advances by the number of items the previous pages returned (not by `limit`), so a server-side page cap below 1000 can't skip items, and an overlap is only a repeat, which the client drops (`rd_client::drop_repeated_ids`; this also covers an add that lands between the first page and the empty terminator of a single-page listing), so every consumer of the listing sees each id once; an id sent as a numeric string is read as the number (`lenient_int`), and a listing whose every entry has an unusable id or hash fails rather than reads as an empty account.
A `createtorrent` answer that QUEUES the add (the account is at its active-download limit: a `queued_id` and no `torrent_id`; the entry isn't in `mylist`) has its queued entry deleted (`queued/controlqueued`, `operation: delete`; a failed delete is logged at error) and fails with the provider-busy 429 (`provider::provider_busy_error`), so `acquire` stops instead of queueing its next candidates, which TorBox would later start with no record or intent, for the mirror to adopt unchecked.
The reconcile or episode-check run then adds nothing more, and a busy staging add ends the upgrade pass.
A 404's error body is logged at debug, not warn: every caller of `get_torrent_info` retries TorBox's spurious `mylist?id=` 404 on purpose, and a caller that gives up on it logs its own outcome (as `rd_client` logs its 404 terminals at debug).
Other error statuses still log their body at warn
