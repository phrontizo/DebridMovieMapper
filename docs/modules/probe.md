# `probe.rs`

Hand-rolled MKV/MP4 track reader; `probe_tracks` fetches the first 4 MB of a CDN URL and extracts audio/subtitle language codes; `verify` checks language requirements (audio passes if any track matches any wanted language: `Lang(l)` → `[l]`, `AnyOf(v)` → `v`, `Original` → `config::original_audio_languages(original_language, spoken_languages)` — the same set acquisition ranks with; languages compare with `lang_eq` (`to_iso639_2` normalisation, which also maps TMDB's non-ISO `cn`→`yue` (Cantonese), `xx`→`zxx` (No Language) and `sh`→`hbs` (Serbo-Croatian), plus macrolanguage membership: `chi` matches `yue`/`cmn`, `hbs` matches `hrv`/`srp`/`bos`/`cnr`, `nor` matches `nob`/`nno`, members never match each other; `to_iso639_2` reads two const tables, `ISO_639_1` and `ISO_639_2_T_TO_B`, and `is_known_language_code`, which `config` uses to vet the language settings, is true for a code in those tables, a macrolanguage or one of its members, and `mul`/`und`); a no-language want (`xx`) drops the audio check; an empty set = no audio check); corrupt/mismatch → blacklist, unknown → accept (`observe` flags such a release `quality.unverified`; the upgrade pass never adopts one); a truncated/under-fetched ranged read → `Transient` (defer + retry, **not** blacklisted).
The MKV parser reads `LanguageBCP47` (0x22B59D, primary subtag) and lets it override the legacy `Language` element (RFC 9559); the `eng` default applies only when neither element is present.
The MKV parser caps the top-level **Segment** to the fetched buffer: a real Segment declares the size of the WHOLE (multi-GB) file, far beyond the 4 MB front read, so its declared end is matched **before** the overrun guard — otherwise the probe wrongly deferred (`Transient`) on essentially every large MKV.
A `Tracks` element whose declared size runs past the fetched buffer is `Transient` even when the cut lands exactly on a TrackEntry boundary, so the targeted recovery fetch runs and the probe never judges a partial track list.
MKV `Language`/`LanguageBCP47` strings are cut at the first NUL byte (RFC 8794 §13 NUL padding) before decoding and trimming, so a padded `jpn\0` reads as `jpn`.
Symmetric to the MP4 large-`moov` recovery, a `Transient` from a Segment child that runs past the front window (a large `Attachments`/`Void`/cover-art block **before** `Tracks`, a `Tracks` element bigger than 4 MB, or a child whose header (id or size vint) the edge of the window cuts, which with a full front read the file's layout repeats on every re-probe) triggers ONE larger targeted fetch (`front_mkv_tracks_extent`, up to `MAX_PROBE_FETCH`) and a re-parse — instead of re-fetching the same 4 MB forever and blacklisting a valid release after the verify deadline (an overrun past the cap, or a `Tracks` still out of reach in the full 8 MB recovery read, e.g. behind a second large pre-`Tracks` block, is accepted-as-unknown rather than churned; a recovery body shorter than 8 MB stays `Transient`).
A **non-faststart MP4** (`ftyp`, `free`, a huge `mdat`, then the `moov` at EOF — no `moov` in the front window) is read at the `moov`'s **exact offset**: `front_mp4_next_box_offset` returns the declared end of the first front box that overruns the window (the `mdat`), and ONE targeted read of `[offset, offset + MAX_PROBE_FETCH)` is parsed for the tracks.
Previously only the 4 MB suffix was tried, which rarely starts on a box boundary, so such files were accepted-as-unknown (`TracksNotFound`) with no language check.
Any failure of the targeted read/parse (a `moov` larger than the 8 MB cap, a size-0 "to EOF" `mdat`, a `416` because the `mdat`'s size lies, garbage) falls back to the old suffix attempt unchanged — it can never introduce a new defer-forever (`Transient`) loop.
The front (offset-0) fetch accepts a **`200 OK`** as well as `206` — a CDN that ignores the `Range` header and streams from byte 0 (**TorBox** does this; Real-Debrid replies `206`) still yields the first window; we read up to `FRONT` bytes then drop the connection.
Requiring `206` made every TorBox probe defer forever even though playback worked (`dav_fs::fetch_cdn_range` already accepted the offset-0 `200`).
The suffix/tail fetch and the targeted trailing-`moov` read still require `206` (a `200` returns the head, not the requested offset).
