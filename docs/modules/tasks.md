# `tasks.rs`

`run_scan_loop` — polls the provider, identifies new torrents (behind a per-tick TMDB circuit breaker, `identify_new_torrent`; see `docs/design/identification.md`), updates VFS (+ `engine.observe`), and `record_mirror_owned` (the **account mirror**: every identified present torrent the engine doesn't already track is recorded as an owned record with empty provenance — owned + upgradeable, not a protected manual class — so the reconciler sees the user's pre-existing library: no duplicate re-acquire, and a season pack's episodes count as owned.
Two kinds of hash are never mirrored: one the engine has blacklisted for ANY title (hash-wide, `all_blacklisted_hashes`) and one with an open staging intent (an upgrade candidate or an acquisition being added, or cut off mid-add).
Nor is a torrent whose cached info lists no emittable video file (a lapsed TorBox entry, one listed with `files: null`, or an archive-only torrent): its record would count its title as owned and available though nothing can be played.
Unowned, its title is acquired as missing, while `acquire` and the upgrade engine still never add a hash already in the account.
An earlier build's record of such a torrent (`Verified`, empty provenance, no quality, no `provides`) is dropped in the same pass, and the torrent is adopted once its files are back.
An existing `Verified` empty-provenance record is reaped as a phantom (store-only, with its authoritative id + selection slots) only when it is no newer than its hash's newest blacklist entry other than a "Dead" one (`Store::blacklist_newest_at_by_hash`).
It leaves alone a `Pending` record, and a record staged or acquired for this title after another title blacklisted the hash (the race it undoes adopts the record before staging blacklists the hash).
`fail_and_reacquire` blacklists a hash only once every delete of it has succeeded, so a record it keeps for a delete retry is never reaped).
The mirror's TMDB `external_ids` lookup stops for the rest of a pass at the first transient failure, and the records it skips get an empty id for `backfill_missing_imdb_ids`; a permanent 4xx is cached as no id.
Before that, the mirror pass also **backfills quality** (`backfill_owned_quality`): an owned `Verified` record with `quality: None` (mirrored before quality capture, or recorded `None` for sitting above the ceiling) has its quality re-derived from its torrent's representative file name (axes it leaves untagged filled from the torrent name), atomically and only while still unset (`Store::set_quality_if_unset`) — the upgrade tick runs the same backfill from the persisted identifications.
It also heals an empty-provenance `Verified` record whose stored quality leaves a resolution or source tier untagged that its file names now tag (older builds read no resolution glued in by underscores, as in `Movie_2019_2160p_UHD_BluRay`, so such a 2160p copy was recorded unknown-lowest and could be replaced by a 1080p release).
The new quality is written only when it tags an axis the stored one left at 0 and untags none, compare-and-set through `Store::replace_quality_if_eq`, keeping the stored `unverified` flag (empty provenance also covers the replacement of a dead mirror copy, which `observe` may have flagged unverified); a record with non-empty provenance keeps its scraped release's quality.
Right after it, the mirror pass also backfills `provides` (`backfill_owned_provides`): a `Verified` show record whose `provides` is empty (written from file names `vfs::parse_se_all` could not decode then, such as `NxM` codes before it learned them; the file lists are the ones cached when each torrent was first identified, except that a list with no emittable video file is fetched again by `refresh_fileless_infos` (see below) until its files are back, so an engine record captured from a listing with no files is filled once they are; until then `monitor_episodes`' `AssumedCoverage` covers for it) gets the episodes its listed torrent's selected video files now decode to (`vfs::episode_files`), atomically and only while still empty (`Store::set_provides_if_empty`).
Then `dedup_owned` (the **duplicate cleanup**: `plan_dedup` finds titles covered by more than one present, **settled** (`Verified`) owned hash (present means servable: at least one listed `downloaded` torrent the instant repair doesn't hide, `RepairManager::hidden_torrent_ids` (`Broken`/`Failed`), that this tick identified with an emittable video file (a copy whose cached info lists no video file, or whose info lookup failed this tick, can't be served or judged by its files); a hidden, not-downloaded or file-less copy is ignored like a `Pending` one) — a `Pending` acquisition (still downloading, or not yet probed/title-checked) is ignored entirely: never ranked, kept, removed or counted as coverage, so it can't displace a playable copy and is judged once `observe` settles it — and, per title, keeps one + marks the redundant ones for removal — a movie keeps the top-priority hash, a show keeps a greedy episode set-cover so complementary packs are all kept.
**Keep-priority = quality first** (`release::quality_rank`: resolution, then source tier, then checked before `unverified` — an untagged axis is 0, so an unknown copy (no recorded quality, or an untagged resolution/source tier) is the lowest at its resolution, while a **known resolution stays a floor**: a 1080p copy with an untagged source outranks a 720p one, and an untagged resolution is the lowest of all) > `quality.score` > currently-served > more episodes > hash; provenance is **not** an axis, so a pre-existing account-mirror copy competes on quality like any engine copy.
Dedup applies the selection repoint's audio-language test (`selection::copy_tags_wrong_audio` under `selection::title_audio_prefs`, i.e. `AUDIO_LANGUAGE` resolved from any record of the title that records its languages): a movie's keep is its top-priority copy whose served (largest) file isn't tagged only with other audio languages, a dub ranked above that keep is kept beside it, and a show copy counts as coverage of an episode only when it doesn't serve it as a dub, or the covered copy does too.
So a right-language copy is never deleted in favour of a better-ranked dub.
The test is inert under `AUDIO_LANGUAGE=original` for a title with no recorded language.
Dedup never consults `MAX_RESOLUTION` (a copy above it is never ranked down for it), so it never trades resolution down (a corrective downgrade stays the upgrade engine's job under `ALLOW_RESOLUTION_DOWNGRADE`).
A show hash is removed only when **every** episode it provides is provided by another kept hash of the **same or better** quality rank (score ignored; judged per episode at the quality of the file each copy would serve for it, `selection::served_rank` of its largest emittable video file carrying the episode, and a copy whose files are known but carry no file for the episode does not cover it, so a mixed-quality mirror pack whose file for an episode is a 480p `.avi` never makes a better single of that episode redundant): the greedy pass runs best-first, and a **second sweep** (lowest-priority first, re-checked against the current kept set so coverage is never lost) reclaims a kept hash that sorted before an equal-quality copy covering it — a better copy is never removed because a worse one covers it (the 2026-11-11 regression).
Empty-`provides` hashes are never removed, nor is a show hash whose files include an emittable video file with no episode code in its name (`holds_codeless_video`: an OVA, a `Season 02/E01 - Title.mkv`, an anime absolute number; `provides` leaves that file out, yet the VFS shows it) unless the hash's own record accounts for that file (an engine record whose `provides` holds the episode `vfs::codeless_episode_files` maps it to; an account-mirror record never does), and a **`Manual`-provenance copy is never placed in the removal set at all** (invariant M-1: manual adds are never auto-removed).
Nor is a movie hash that is a multi-film collection (`multi_feature_hashes`: more than one SELECTED video of at least 700 MB, `acquire::FEATURE_MIN_BYTES`): the mirror identifies such a torrent as one film, yet the VFS shows every film in it, and no kept copy provides the others.
Nor does a collection take the film's keep slot.
The keep is the best single-film copy, so a collection, whose record quality is its largest file's and possibly another film's, never makes a single copy redundant.
Accepted consequence of no mirror protection: when a mirror copy loses to a better engine copy, the title's survival rests on that engine copy, which Trigger A/B may later remove (the lifecycle's own mirror protection — `removal_hashes`/`engine_hashes` — is unchanged).
A title with an owned record added within `UPGRADE_IDLE_SECS` (`fresh_dedup_groups`: an upgrade swap may be in flight) is left out of the plan, dry-run log included, until the window passes.
Where dedup prefers the old copy it would otherwise delete the just-staged one while the swap prunes the old one, losing both: a corrective downgrade, an over-ceiling pack correction, or a consolidation pack of equal quality rank but a lower score than the singles it covers.
The swap also re-checks that the staged copy is still owned before it prunes (`upgrade::prune_behind_staged`).
Dry-run by default; `DEDUP_REMOVE_DUPLICATES=true` enables idle-gated deletion + owned-record/selection cleanup (`Store::forget_owned`)).
Then `selection::repoint_to_better_copies` (**serve the best copy present**: every existing `selection` slot whose served copy is present, settled and owned is repointed — idle-gated, compare-and-set via `Store::repoint_selection_if` — to another present `Verified` owned copy of the same title that supplies it (lists the episode in `provides` and has an emittable video file with that episode code; a movie: its largest emittable video file) at a STRICTLY higher `quality_rank`, so e.g. a pre-existing or re-added REMUX season no longer hides behind an engine-acquired BluRay pack's slots; nothing is deleted, and equal-rank copies never churn a slot; an episode two or more present settled owned copies supply with no slot at all gets one on the best of them, `selection::plan_missing_episode_slots`).
The per-tick body is `scan_tick` (state in `ScanState`), which the tests drive directly.
The hashes `observe` deleted this tick (it returns them) are dropped from the listing before the VFS, mirror, dedup, repoint and reaper see it, so a release rejected after it was shown leaves the VFS in the same tick.
A listed `downloaded` torrent whose cached identification lists no emittable video file (TorBox can report a finished torrent with `files: null`, and the identification is otherwise fetched once per id) has its files fetched again by `refresh_fileless_infos`, before new torrents are identified.
The first fetch comes `FIRST_INFO_REFRESH_AFTER` (5 min) after the scan loop first notices the torrent (the schedule is in memory, so a restart notices them all again), then again `INFO_REFRESH_AFTER` (1 h) after every fetch that fails or still finds none, at most `MAX_INFO_REFRESHES_PER_TICK` (10) per tick.
A fresh list with an emittable video file replaces the cached one (seen state plus `matches`), and the torrent is identified again from it (`resolve_metadata`): the cached identification went by the torrent name alone and may have guessed a film where the files show a pack.
An engine copy keeps its authoritative identification.
A refresh TMDB can't identify (its search failed, or the tick's breaker is already set) changes nothing: the torrent stays file-less, out of the VFS and the mirror, and is tried again after `TMDB_RETRY_AFTER` (15 min), since keeping the torrent-name guess with the fresh files would make it permanent.
One TMDB circuit breaker (`resolve_metadata_unless_tmdb_down`) covers the tick's refreshes and its identification batch, so an outage costs one retry budget per tick.
Once a refresh succeeds, the VFS shows the torrent, the mirror can adopt it, and the quality and `provides` backfills complete an existing record.
A cached list with files is never swapped for an empty one.
Before identifying anything, the scan loop runs two passes over the listing.
On every trusted listing, `upgrade::sweep_staging_intents` handles each abandoned staging intent: every intent an earlier process left (one this process holds no in-memory note of, `Store::local_staging_age`), and this process's intents open for `upgrade::STAGING_ABANDONED_AFTER_SECS` (1 h) by the monotonic clock.
With no such intent this costs one store read.
It deletes the torrent of each abandoned intent whose hash is not owned, and closes an intent whose hash is owned without deleting anything.
An intent whose hash is not listed is closed only once deleting its recorded torrent id succeeds, or once it is `STAGING_LISTING_LAG_SECS` (10 min) old, so a lagging TorBox listing cannot let the mirror adopt the torrent.
Deleted torrents are dropped from the tick's listing.
It is not idle-gated.
A listed torrent whose intent was open when the tick started (read before the listing) or is still open after the sweep, and whose hash isn't yet recorded as owned with an authoritative entry (`staging_unrecorded`: a candidate being staged or acquired, one whose rejection delete failed, or one the upgrade job discarded while `observe` ran), is kept out of the tick's VFS, identification and mirror.
It is not shown, identified from its file name or cached, and the tick after it is recorded (`record_staged`, or `acquire`'s `Pending` record) identifies it through its authoritative entry.
`observe` still sees the full listing, and dedup deletes every listed id of a hash it removes but judges only copies in the tick's data.
The tick takes the repair replacements (`take_repair_replacements`) before the listing and puts them back (`RepairManager::restore_repair_replacements`, where an entry recorded since the take wins) when it is skipped for a failed or suspect listing, so the next tick still reuses the repaired torrent's identification.
Then the same-hash duplicate deletion (`dedup_torrents_by_hash`) keeps the first `downloaded` torrent listed per hash (the newest) and deletes the other `downloaded` torrents with that hash.
It is always on, not governed by `DEDUP_REMOVE_DUPLICATES`, and gated on `all_idle`; a torrent id listed twice in one listing (a page-boundary repeat) is skipped, never deleted; both provider clients already drop such repeats (`rd_client::drop_repeated_ids`), so this skip is a second guard.
A wholesale-empty provider listing while torrents were known is treated as suspect until it has been seen three times in a row (`EMPTY_LISTINGS_BEFORE_TRUSTED`) and has stayed empty for at least 10 minutes (`MIN_EMPTY_DURATION`), whatever `SCAN_INTERVAL_SECS` is: the scan loop then runs only `observe` and leaves the VFS, the identification cache and mirror/dedup/repoint/reaper untouched, and `reconcile_wanted` and `monitor_episodes` follow the same verdict (`listing_is_suspect`: an empty listing while `Store::has_matches`), counting owned titles/episodes as available and planning no removal.
On start-up and on every daily prune tick, before it fetches the listing, the scan loop drops blacklist entries older than 30 days (`Store::prune_blacklist_before`) and the `upgrade_checks` cursor rows of titles no longer owned (`Store::prune_upgrade_checks_not_owned`).
On the first trusted listing on or after the daily prune tick (`ScanState::maintenance_due`, so a failed or suspect listing on that tick does not postpone it a day), `backfill_missing_imdb_ids` fills the empty `imdb_id` of present `Verified` owned records (written by the mirror when TMDB `external_ids` failed transiently) via the atomic `Store::set_imdb_id_if_empty`: one lookup per title per pass, and a transient failure ends the pass.
That tick also runs `reap_absent_mirror_owned` (the **mirror-record reaper**: a `Verified` **empty-provenance** account-mirror owned record whose hash has left the provider listing entirely is dropped — with its authoritative-id + selection entries — so the otherwise-append-only `owned` table can't grow unbounded as a user churns their debrid account; apart from an `acquire` for the same slot (`AcquisitionEngine::reap_lapsed_superseded`), nothing else cleans an absent mirror record, since dedup/`observe`/Trigger-A/B all ignore it.
Store-only — the torrent is already gone, so there's no provider deletion and no stream to interrupt, hence no idle-gate; guarded off a wholesale-empty listing like `observe`.
The prune tick only notes the absent records (`ScanState::reap_candidates`); the next trusted listing reaps those still absent, so one listing that misses a present torrent (a page shift from a delete made outside this process) reaps nothing.
A wrongful reap still loses state: `record_mirror_owned` re-mirrors the hash next tick as a bare record (file-name quality, no TMDB languages, an empty IMDB id while TMDB fails), and its selection slots and authoritative id are gone.
Engine/provenance-bearing records are left to the acquire/reconcile lifecycle).
Also hosts the SP2 Trakt jobs: `sync_trakt` (materialise each user's `wanted` set), `reconcile_wanted` (movie acquire/re-acquire + movie Trigger-A/B removal + show Trigger-B removal), and `monitor_episodes` (show episode acquisition + Trigger-A finish removal).
`monitor_episodes` keeps an in-memory `AssumedCoverage` across its runs (created once by `scheduler::run`).
When `acquire` answers an episode with `Acquired` naming a present `Verified` show copy whose `provides` is empty, later runs count that episode as covered by the copy instead of spending a scrape and a provider listing on it every run.
An entry is dropped once its hash is missing from a trusted (non-suspect) listing, or its record is gone, unsettled or lists episodes; a restart asks once again.
The destructive `execute_remove` is **idle-gated** (`UPGRADE_IDLE_SECS`, like dedup/upgrade) so a Trigger-A/B removal never interrupts an active stream — important in a multi-user household; a deferred removal is left intact and retried on a later idle tick
